## 1. 인덱스 없는 상태 (2026-08-13)

`users_id` 를 포함한 인덱스가 하나도 없는 상태. 남아 있는 것은 각 테이블의 PRIMARY 와
`schedules` 의 `folders_id` FK 인덱스뿐이다. InnoDB 가 FK 컬럼에 인덱스를 강제하므로
`users_id` FK 5개를 먼저 떼어야 이 상태를 만들 수 있다.

```
EXPLAIN   type=ALL  key=NULL
```

```
-> Filter: ((schedules.status = 'ACTIVE') and (schedules.users_id = 100)
            and (schedules.title like '%zzsearch%'))
     (cost=1370 rows=74.8) (actual time=4.52..10.8 rows=4 loops=1)
   -> Table scan on schedules
     (cost=1370 rows=13462) (actual time=0.154..8.53 rows=13750 loops=1)
```

13,750행을 통째로 읽어 4건을 건진다. 5개 테이블 합치면 **요청 하나가 54,176행**을 훑는다.

헤비 유저(users_id=65)도 같은 13,750행을 읽는다. 풀스캔은 누가 검색하든 테이블 전체를
읽으므로 사용자별 차이가 없다. 인덱스를 걸면 여기가 갈린다.

애플리케이션 JOIN 쿼리는 `attachments` 8,362행을 훑은 뒤 `folders` PK 를 4번 조회한다.

```
-> Nested loop inner join  (cost=1660 rows=8150) (actual time=12..12 rows=4 loops=1)
    -> Sort: a.created_at DESC  (actual time=12..12 rows=4 loops=1)
        -> Filter: ((a.attachments_type = 'FILE') and (a.status = 'ACTIVE')
                    and (a.users_id = 100) and (a.file_name like '%zzsearch%'))
             (actual time=4.62..11.9 rows=4 loops=1)
            -> Table scan on a  (actual time=0.0255..9.25 rows=8362 loops=1)
    -> Single-row index lookup on f using PRIMARY (folders_id=a.storage_id)
         (actual time=0.00484..0.00488 rows=1 loops=4)
```

### 검색 컬럼에 단독 인덱스를 걸면

인덱스가 하나도 없는 이 상태에서만 깨끗하게 잴 수 있다. 복합 인덱스가 살아 있으면
`users_id` 가 이미 범위를 좁혀버려 검색 컬럼 인덱스의 효과를 분리할 수 없다.

```sql
CREATE INDEX tmp_title_only ON schedules (title);
EXPLAIN SELECT * FROM schedules WHERE title LIKE '%zzsearch%';
```

```
1  SIMPLE  schedules  ALL  (key = NULL)
```

**만들어도 쓰지 않는다.** 에러도 경고도 없이 그냥 풀스캔을 고른다.

```
-> Filter: (schedules.title like '%zzsearch%')
     (cost=1406 rows=1535) (actual time=0.0633..13.3 rows=800 loops=1)
   -> Table scan on schedules
     (cost=1406 rows=13815) (actual time=0.06..9.16 rows=13750 loops=1)
```

애플리케이션 쿼리 형태(`users_id` + `status` + `LIKE`)로 해도 `type=ALL / key=NULL` 로
같다. 800건이 걸린 것은 `users_id` 조건이 없어 200명 × 4행이 모두 매칭됐기 때문이다.

> 이전 측정은 `(users_id, status, title)` 복합 인덱스로 했는데, 앞의 `users_id` 가 이미
> 50행으로 좁혀 놓은 상태였다. `LIKE '%x%'` 가 0.107ms 로 빨랐던 것은 title 인덱스 덕이
> 아니라 **채택하려던 복합 인덱스가 이미 일하고 있었기 때문**이다. 검색 컬럼 단독 인덱스는
> 그때 한 번도 재보지 않았다.

### 관찰

**단일 요청은 87.0ms 로 빠르다.** 혼자 쓰면 아무 문제가 없다. 경합이 생기는 순간 무너진다.

**처리량이 20.9 req/s 에서 고정된다.** 동시 3명부터 천장이고, 그 뒤로 요청을 30배
밀어넣어도 변하지 않는다. 처리되지 못한 요청이 줄만 길어진다.

Little's Law 를 반대로 써서 맞춰보면 들어맞는다.

```
동시  15    15 ÷ 20.8 =   721ms      실측 p95   898ms
동시 100   100 ÷ 21.0 = 4,762ms      실측 p95 5,310ms
```

**응답이 느린 게 아니라 처리 능력이 바닥난 것이다.**

**수용 한계는 동시 10명.** 15명에서 SLI 가 41.68% 로 떨어진다. **목표(동시 50명)에서는
3.62%** 로, 5분의 1도 못 간다.

실패율은 전 구간 0% 다. 죽은 요청은 없고 느려지기만 했다. 동시 100명에서 최장 응답이
15.9초까지 갔지만 k6 타임아웃(60초)에는 닿지 않았다.

### 쿼리를 17% 줄였는데 처리량은 1.5% 만 올랐다

`lower()` 를 걷어내기 전후를 같은 조건으로 재봤다.

| | lower() 있음 | lower() 없음 | |
| --- | --- | --- | --- |
| 쿼리 하나 (EXPLAIN ANALYZE) | 13.0ms | 10.8ms | **-17%** |
| 처리량 천장 | 20.6/s | 20.9/s | +1.5% |
| 수용 한계 | 동시 10명 | 동시 10명 | 동일 |

`EXPLAIN ANALYZE` 는 한가한 DB 에서 쿼리 하나만 잰 값이다. 실제 부하에서는 2 vCPU 를 앱과
DB 가 나눠 쓰고, 요청 하나에 Hibernate 의 쿼리 해석·트랜잭션·직렬화가 모두 붙는다.
**`lower()` 는 그 전체 비용 중 작은 조각**이었다.

단일 쿼리 개선폭이 그대로 처리량으로 옮겨가지 않는다는 뜻이다.

### 사용자군을 바꿔도 같았다

인덱스가 없으면 누가 검색하든 테이블 전체를 훑으므로, 평균 유저만 쓸 때와 헤비 유저를 섞을
때의 차이가 없었다.

| 동시 요청 | avg (195명) | all (200명) |
| --- | --- | --- |
| 1 | 64.5ms | 58.4ms |
| 10 | 534.1ms | 538.4ms |

*(단계당 30초로 잰 값. 이후 측정은 실제 트래픽에 가깝도록 `all` 로 통일한다.)*

### 단계 시간을 30초에서 2분으로 늘렸다

처음에는 단계당 30초로 쟀는데, 모니터링 스크래이프 간격이 60초라 **그래프에 단계당 점이
하나도 안 찍혔다.** 표는 정확한데 추세를 볼 수 없었다.

단계를 2분으로 늘리니 단계당 점이 2개씩 찍혀 계단이 보인다. 낮은 구간에서 값이 조금 높게
나왔지만(오래 돌릴수록 더 많은 사용자를 순회해 캐시 적중이 떨어진다), **처리량 상한과 수용
한계는 동일**했다.

## 2. 복합 인덱스 `(users_id, status)` (2026-08-13)

엔티티에 정의된 인덱스를 복구한 상태. 첨부는 검색 시 타입까지 거르므로
`(users_id, status, attachments_type)` 3컬럼이다.

### 실행 계획

`IGNORE INDEX` 로 같은 세션에서 두 방식을 나란히 실행했다. 인덱스를 붙였다 뗐다 하지 않으니
캐시 상태가 같아 비교가 깨끗하다.

```
복합 인덱스
-> Filter: (schedules.title like '%zzsearch%')
     (cost=13.1 rows=5.56) (actual time=0.0449..0.157 rows=4 loops=1)
   -> Index lookup on schedules using idx_schedules_users_status
        (users_id=100, status='ACTIVE'), with index condition: (status = 'ACTIVE')
     (cost=13.1 rows=50) (actual time=0.0424..0.136 rows=50 loops=1)

IGNORE INDEX (강제 풀스캔)
-> Filter: ((schedules.status = 'ACTIVE') and (schedules.users_id = 100)
            and (schedules.title like '%zzsearch%'))
     (cost=1405 rows=3.84) (actual time=7.36..15.6 rows=4 loops=1)
   -> Table scan on schedules
     (cost=1405 rows=13811) (actual time=0.063..13.1 rows=13750 loops=1)
```

| | 강제 풀스캔 | 복합 인덱스 | |
| --- | --- | --- | --- |
| 실행 방식 | Table scan | **Index lookup** | |
| 읽은 행 | 13,750 | **50** | 275배 감소 |
| 스캔 시간 | 13.1ms | **0.136ms** | 96배 |
| 쿼리 전체 | 15.6ms | **0.157ms** | 99배 |

`Table scan` 이 `Index lookup` 으로 바뀌고, 그 사용자의 50행만 읽어 `LIKE` 로 4건을 고른다.

5개 테이블 전부 `type=ref` 로 인덱스를 탄다.

| 테이블 | 인덱스 없음 | 복합 인덱스 | key |
| --- | --- | --- | --- |
| folders | 2,107 | 10 | idx_folders_users_status |
| schedules | 13,750 | 50 | idx_schedules_users_status |
| links | 21,606 | 80 | idx_links_users_status |
| texts | 8,351 | 30 | idx_texts_users_status |
| attachments | 8,362 | 30 | idx_attachments_users_status |
| **합계** | **54,176** | **200** | |

**요청 하나가 읽는 행이 271배 줄었다.**
`Extra` 는 전부 `Using index condition; Using where` 로 ICP 가 동작한다.

> `EXPLAIN` 의 `rows` 는 `1` 로 나왔지만 `EXPLAIN ANALYZE` 의 실제 값은 `50` 이었다.
> 앞의 것은 통계 샘플링에서 나온 추정치라 실제와 어긋난다. **읽은 행을 확인하려면
> `EXPLAIN` 이 아니라 `EXPLAIN ANALYZE` 를 봐야 한다.**

### 인덱스가 사용자별 편차를 만든다

평균 유저(users_id=100, 일정 50건)와 헤비 유저(users_id=65, 일정 800건)를 같은 조건으로
비교했다.

| | 강제 풀스캔 | 복합 인덱스 | |
| --- | --- | --- | --- |
| 평균 유저 | 13,750행 · 15.6ms | 50행 · 0.157ms | 99배 |
| 헤비 유저 | 13,750행 · 18.7ms | 800행 · 1.72ms | 11배 |

```
인덱스 없음   평균 13,750행 = 헤비 13,750행     차이 없음
복합 인덱스   평균     50행 · 헤비   800행      16배 차이
```

**인덱스를 걸기 전에는 사용자별 편차가 없었다.** 누가 검색하든 테이블 전체를 훑으니
모두 똑같이 느렸다. 인덱스를 걸자 각자 자기 데이터만 읽게 되면서 편차가 드러났다.

헤비 유저도 1.72ms 라 SLO(700ms) 대비 여유는 충분하다. 다만 **개선폭이 99배가 아니라
11배**이므로, 사용자당 행 수가 더 커지면 이쪽부터 먼저 SLO 를 벗어난다.

### 애플리케이션 쿼리 (folders JOIN)

첨부 검색은 N+1 을 없애며 `folders` 와 JOIN 하도록 바꾼 구조라 따로 확인했다.

```
복합 인덱스
-> Nested loop inner join  (cost=11.7 rows=30) (actual time=1.06..1.06 rows=4 loops=1)
    -> Sort: a.created_at DESC  (actual time=1.05..1.05 rows=4 loops=1)
        -> Filter: (a.file_name like '%zzsearch%')  (actual time=0.935..1.03 rows=4 loops=1)
            -> Index lookup on a using idx_attachments_users_status
                 (users_id=100, status='ACTIVE', attachments_type='FILE')
               (actual time=0.0381..0.119 rows=30 loops=1)
    -> Single-row index lookup on f using PRIMARY (folders_id=a.storage_id)
       (actual time=0.00275..0.00279 rows=1 loops=4)

IGNORE INDEX (강제 풀스캔)
-> Nested loop inner join  (cost=1697 rows=8361) (actual time=20.3..20.3 rows=4 loops=1)
    -> Sort: a.created_at DESC  (actual time=20.2..20.2 rows=4 loops=1)
        -> Filter: (...)  (actual time=8.12..20.2 rows=4 loops=1)
            -> Table scan on a  (actual time=0.027..15.5 rows=8362 loops=1)
    -> Single-row index lookup on f using PRIMARY (actual time=0.00435 rows=1 loops=4)
```

읽는 행 8,362 → 30, 쿼리 시간 20.3ms → 1.06ms 로 **19배** 줄었다.

`a` 는 `ref`, `f` 는 `eq_ref PRIMARY` 로 붙는다. **N+1 이 없다.** `loops=4` 는 검색 결과
4건에 대해서만 보관함을 조회한다는 뜻이다.

`Extra` 에 `Using filesort` 가 있지만 **정렬 대상이 4행**이라 비용이 0.017ms 다.
`ORDER BY created_at DESC` 가 필터 뒤에 오기 때문이다.

### 커버링 인덱스로 더 갈 수 있나 — 전망

검색 컬럼을 인덱스에 넣으면 인덱스를 훑으며 `LIKE` 를 평가할 수 있어, 안 맞는 행은
테이블에 가지 않는다. 지금은 북마크 조회가 30회인데 4회로 줄어든다.

그런데 인덱스 조회 전체가 **0.119ms** 다. 줄일 수 있는 여지가 0.1ms 안쪽이다.

```
사용자당 200행뿐이라 복합 인덱스가 이미 충분히 좁혔다
커버링으로 더 좁힐 여지가 거의 없다
반면 인덱스 크기는 검색 컬럼만큼 커진다
```

**효과는 미미하고 비용은 확실할 것으로 예상**한다. 실제로 그런지 재본다.

### `key_len` 으로 본 앞 와일드카드 — 이 측정은 근거가 되지 못했다

`(users_id, status, title)` 인덱스를 만들고 `LIKE` 모양만 바꿔 비교했던 기록이다.

| | type | key_len | rows | 실측 |
| --- | --- | --- | --- | --- |
| `LIKE 'zzsearch%'` | **range** | **1,030** | **1** | 0.047ms |
| `LIKE '%zzsearch%'` | ref | 9 | 50 | 0.107ms |

```
앞 고정   key_len 1,030 = users_id(8) + status(1) + title(1,021)
앞 열림   key_len     9 = users_id(8) + status(1)
```

여기서 얻은 사실 자체는 맞다. **앞이 고정되면 `title` 까지 인덱스로 범위를 만들고, 열려
있으면 `users_id`·`status` 까지만 쓴다.**

문제는 이걸로 **"검색 컬럼에 인덱스를 걸어도 소용없다"** 를 주장할 수 없다는 점이다.
인덱스 앞에 `users_id` 가 있어 이미 50행으로 좁혀진 상태였다. `LIKE '%x%'` 가 0.107ms 로
빨랐던 것은 title 인덱스 덕이 아니라 **채택하려던 복합 인덱스가 이미 일하고 있었기
때문**이다.

검색 컬럼 단독 인덱스는 인덱스를 전부 걷어낸 상태에서 따로 쟀다. 1장의

## 3. 병목은 어디로 갔나 (2026-08-13, `lower()` 제거 이전 측정)

아래는 `lower()` 를 걷어내기 전 코드로 잰 값이다. 처리량 수치가 1·2장과 다르다.
CPU 비율과 프로파일링 결과 자체는 재측정 후에도 달라질 이유가 없어 그대로 남긴다.

복합 인덱스로 목표는 넘겼지만 **CPU 는 여전히 100%** 였다. 다만 그 안의 비율이 바뀌었다.

| | 시스템 CPU | JVM 프로세스 CPU | 나머지 |
| --- | --- | --- | --- |
| 인덱스 없음 | 100% | 5~9% | ~92% |
| 복합 인덱스 | 100% | ~50% | ~50% |

같은 서버에 앱과 MySQL 컨테이너뿐이므로 "나머지" 는 DB 다.

```
인덱스 없음   DB 가 5만여 행을 훑느라 1.8 코어를 쓴다
             앱은 초당 20건만 받아 0.1 코어만 쓴다 — 놀고 있다
복합 인덱스   DB 가 200행만 읽으니 부하가 준다
             앱이 초당 200건 가까이 처리하느라 1 코어를 쓴다 — 이제 앱이 바쁘다
```

**병목이 DB 에서 앱으로 옮겨갔다.** 읽는 행을 271배 줄였는데 처리량은 10.7배만 오른 이유가
이것이다. 스캔이 사라지자 그 뒤에 가려 있던 비용이 드러났다.

### 프로파일링 (async-profiler, 동시 50명 · 60초)

```

 66.5%   핸들러 호출
  58.5%    트랜잭션 안
   50.8%     통합검색 search()
    10.2%      첨부 검색
     9.2%      보관함 검색
     9.2%      일정 검색
     7.3%      링크 검색
     7.0%      텍스트 검색
     5.8%      사용자 조회        ← 검색과 무관
   4.0%      트랜잭션 커밋
   3.3%      트랜잭션 시작
  7.1%     응답 직렬화 (Jackson)

```

**단일 병목이 없다.** 5개 검색이 43% 를 고르게 나눠 쓴다. 하나를 고쳐도 5로 나뉜 몫만 준다.
**5번 반복하는 구조 자체가 비용**이다.

그리고 각 검색 안을 보면 대부분이 **Hibernate 의 쿼리 해석·JDBC 실행 준비**다.

```
7.3%  링크 검색
 6.5%   getResultList
  4.4%    ConcreteSqmSelectQueryPlan.interpret   ← 쿼리 해석·변환
```

**쿼리를 실행하는 것보다 쿼리를 만드는 데** 더 쓴다. 인덱스로 스캔을 271배 줄이니 ORM
오버헤드가 드러난 것이다.

### 그래서 FULLTEXT 는 지금 답이 아니다

`LIKE` 를 `MATCH AGAINST` 로 바꿔도 줄어드는 건 이미 작은 부분이다. DB 실행이 병목이 아니기
때문이다. 사용자당 행 수가 수천을 넘어 스캔이 다시 커지면 그때 다시 볼 만하다.

### 다음 후보

```
① @Transactional(readOnly = true)   트랜잭션 시작·커밋 7.3% 중 일부
② UsersService.findById 제거        5.8%. 검색에 왜 필요한지 확인
③ 5번 반복 구조                      43%. 병렬화하면 요청 하나가 커넥션 5개를 점유한다
```

## 측정하며 겪은 것

### DBeaver 에서 스크립트가 실행되지 않았다

`Ctrl+Enter` 는 **커서가 놓인 문장 하나만** 실행한다. 파일 전체를 돌리려면 `Alt+X`(Execute
script)를 써야 한다. 그전까지 각 파일의 마지막 확인 SELECT 만 실행되고 INSERT · DELETE 는
한 번도 돌지 않았다.

확인 쿼리가 그럴듯한 값을 돌려주기 때문에 **실행된 것처럼 보였다.**

### 404 응답이 SLI 100% 로 잡혔다

토큰이 삭제된 유저 것이라 모든 요청이 404 였는데, 표에는 이렇게 나왔다.

```
동시 10   SLI 100.00%   p95 30.9ms   처리량 511/s   실패율 100.00%
```

**SLI 는 "700ms 이내에 응답했는가" 만 본다.** 에러 응답은 빠르니 SLI 가 만점이 된다.
표에 실패율을 같이 넣어두지 않았다면 이 결과를 그대로 믿었을 것이다.

**응답 시간 지표는 성공 여부와 함께 봐야 한다.**

### 시드가 검색어를 모든 행에 심고 있었다

옛 시드는 모든 행 이름에 `loadtest` 를 넣었고 검색어도 `loadtest` 였다. `LIKE` 가 아무것도
걸러내지 못해 **필터 비용이 측정에서 빠져 있었다.**

### `storage_id` 가 없는 폴더를 가리켰다

시드가 `storage_id = 1` 을 하드코딩했는데 teardown 으로 그 폴더가 지워졌다. FK 제약이 없어
INSERT 는 통과했지만 JOIN 이 0행을 반환했다.

```
Single-row index lookup on f using PRIMARY (folders_id=a.storage_id)
  rows=0 loops=10
```

애플리케이션 검색은 `folders` 와 JOIN 하므로, 그대로 뒀다면 **모든 검색이 0건인 상태로
부하 테스트**를 돌릴 뻔했다.

### 인덱스를 지우려는데 FK 가 잡고 있었다

```
Cannot drop index 'idx_schedules_users_status': needed in a foreign key constraint
```

InnoDB 는 **FK 컬럼에 인덱스를 반드시 요구한다.** `(users_id, status)` 의 맨 앞이 `users_id` 라
이 인덱스가 FK 인덱스를 겸하고 있었다. 인덱스 없는 상태를 만들려면 `users_id` FK 5개를 먼저
떼야 했다.

### 토큰 앞쪽이 전부 헤비 유저였다

k6 가 토큰을 `TOKENS[(__VU - 1) % TOKENS.length]` 로 골랐는데, 토큰 앞 5개가 헤비 유저다.

```
동시 5명   tokens[0..4]  → 전원 헤비 유저
동시 30명  tokens[0..29] → 6명 중 1명이 헤비
```

**낮은 동시 구간일수록 헤비 유저만 측정하게 된다.** 사용자군을 고를 수 있게 하고
(`-e USERS=avg|heavy|all`), 반복 횟수를 더해 풀 전체에 퍼뜨리도록 바꿨다.

### 데이터 구성을 다시 잡았다

처음에는 유저 30명 × 1,000행이었다. 두 가지가 문제였다.

```
유저당 1,000행    "일반 유저" 라 부르기 어렵다. 일정을 천 개 만드는 사용자는 없다
전체 39,000행     DAU 수백 규모 서비스의 누적 데이터로는 적다
```

그리고 이 둘이 인덱스 효과를 정한다.

```
인덱스 개선의 천장 = 전체 행 수 ÷ 그 사용자의 행 수
  30명 × 1,000행    39,000 ÷ 1,000 =  39배
  200명 × 200행     54,000 ÷   200 = 270배
```

**전체 행 수는 서버 부하를, 유저당 행 수는 인덱스 효과를 정한다.** 둘을 따로 조절해야 한다.
유저 수를 200명으로 늘리고 유저당을 200행으로 줄이니, 전체 규모는 비슷한데 훨씬 현실적이 됐다.

문자열도 짧았다. `'item text 4821'` 은 14자인데 실제 메모는 훨씬 길다. 행이 작으면 페이지당
행이 많아져 **스캔 비용이 실제보다 싸게 나온다.** 132자로 늘렸다.
