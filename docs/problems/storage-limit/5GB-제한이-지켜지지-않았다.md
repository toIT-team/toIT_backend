# 5GB 제한을 걸었는데 지켜지지 않았다 — 동시 요청 경쟁 조건 해결기

> 계정당 저장 용량을 5GB로 제한해 뒀습니다. 그런데 **기기 두 대에서 동시에 사진을 올리면
> 그냥 넘어갑니다.** `@Transactional`을 붙여도, 격리수준을 확인해도 막히지 않았습니다.
> 왜 안 막히는지 숫자로 확인하고, 락을 걸어 해결하기까지의 기록입니다.
> 중간에 막힐 때마다 무엇을 공부해야 했는지도 함께 적었습니다.

---

# 1. 어떤 구조인가

toIT는 링크·메모·이미지·파일을 보관함에 모아 두는 서비스입니다. 사진과 파일은 S3에 보관하고,
**계정당 5GB**를 넘으면 업로드를 거부합니다.

성능을 위해 파일이 서버를 거치지 않고 S3로 바로 올라갑니다. 그래서 저장이 세 단계입니다.

```
① 업로드 URL 요청   서버가 용량을 확인하고 업로드 URL을 발급
② 직접 업로드       앱이 S3로 파일을 바로 전송
③ 저장 확정         서버가 DB에 최종 반영
```

용량 검사는 ①에서 합니다. 그 안에서 이런 일이 순서대로 일어납니다.

```
사용량 합산  →  5GB 넘는지 검증  →  예약 저장
```

---

# 2. 동시에 올리면 그냥 넘어간다

**합산과 저장 사이가 비어 있습니다.**

동시에 들어온 요청들은 서로가 저장하기 전에 사용량을 읽습니다. 그러면 **전부 같은 값을 보고
전부 통과**합니다.

```
남은 용량 15MB, 요청 하나가 15MB일 때

[A] 사용량 합산 → 4.985GB
[B] 사용량 합산 → 4.985GB    ← 아직 아무도 저장하지 않았다
[A] 4.985 + 0.015 = 5.0GB → 통과
[B] 4.985 + 0.015 = 5.0GB → 통과
[A] 예약 저장
[B] 예약 저장
                              → 5.015GB. 15MB 초과
```

## 얼마나 뚫리는지 재봤다

말로만 두면 *"발생할 수 있습니다"* 로 끝납니다. k6로 재현했습니다.

남은 용량을 **요청 1건 분량(15MB)** 으로 맞췄습니다. 한 요청은 사진 3장(각 5MB)이라 15MB고요.
**정상이라면 1건만 통과하고 나머지는 전부 거부**되어야 합니다.

| 동시 요청 | 통과 | 초과 |
| --- | --- | --- |
| **2** | **2** | **15MB** |
| 5 | 5 | 60MB |
| **10** | **10** | **135MB** |
| 20 | 10 | 135MB |

**동시 2건에서 이미 뚫립니다.** 기기 두 대에서 사진 3장씩 올리는 것만으로요.

그리고 이상한 게 보입니다. **동시 20에서도 통과가 10건에서 멈춥니다.**

> **여기서 하나 배웠습니다 — 뚫리는 양의 상한을 커넥션 풀이 정하고 있었습니다.**
>
> HikariCP 기본 풀 크기가 10입니다. 커넥션을 못 잡은 요청은 대기하는데, 그 사이 앞선 요청이
> 커밋되어 정상적으로 차단됩니다. 즉 **경쟁 창의 크기를 동시 요청 수가 아니라 커넥션 풀이
> 결정**하고 있었습니다.
>
> 버그의 최대 피해량이 우리가 설정한 적도 없는 값에 묶여 있었던 셈입니다.

# 3. `@Transactional` 을 붙여봤다 — 안 막힌다

가장 먼저 떠오른 건 트랜잭션이었습니다. URL 요청 메서드에 `@Transactional`을 붙였습니다.

**그대로 뚫렸습니다.**

> **여기서 짚고 갈 것 — 트랜잭션의 원자성은 상호배제가 아닙니다.**
>
> `@Transactional`이 보장하는 건 **한 요청 안의 작업을 한 덩어리로 묶는 것**입니다.
> 중간에 실패하면 전부 되돌리고, 성공하면 전부 반영하는 것이죠.
>
> 그런데 **요청마다 트랜잭션이 따로 만들어집니다.** A의 트랜잭션과 B의 트랜잭션은 별개라
> 서로가 무엇을 하는지 알지 못합니다.
>
> ```
> 원자성(Atomicity)   내 작업을 전부 하거나 전부 안 하거나
> 상호배제            남이 끼어들지 못하게 막는 것   ← 이건 다른 이야기
> ```
>
> 트랜잭션은 앞을 보장하지 뒤를 보장하지 않습니다.

# 4. 격리수준을 올리면 되지 않나 — 여기서 한참 헤맸다

ACID에서 조절할 수 있는 건 격리(Isolation)뿐입니다. 격리수준을 공부하기 시작했습니다.

> **배운 것 — 격리수준 4개와 이상현상 3개**
>
> 격리수준은 **"다른 트랜잭션의 작업이 나에게 얼마나 보이느냐"** 를 정하는 설정입니다.
> 느슨할수록 빠르고 엄격할수록 안전합니다.
>
> | 격리수준 | Dirty Read | Non-repeatable Read | Phantom Read |
> | --- | --- | --- | --- |
> | READ UNCOMMITTED | O | O | O |
> | READ COMMITTED | X | O | O |
> | **REPEATABLE READ** (MySQL 기본) | X | X | X\* |
> | SERIALIZABLE | X | X | X |
>
> - **Dirty Read** — 아직 커밋 안 된 남의 변경을 읽음. 롤백되면 없던 값을 본 셈
> - **Non-repeatable Read** — 같은 행을 두 번 읽었는데 값이 다름
> - **Phantom Read** — 같은 조건으로 두 번 조회했는데 **행 개수**가 다름
>
> \* InnoDB는 갭 락 덕분에 REPEATABLE READ에서도 팬텀 리드를 대체로 막습니다.

여기까지 읽고 **"그럼 MySQL 기본값이 REPEATABLE READ니까 이미 막혀 있어야 하는 것 아닌가"**
싶었습니다. 그런데 안 막힙니다.

> **더 배운 것 — 우리 문제는 표준 3현상 어디에도 없습니다.**
>
> 우리 상황은 이렇습니다.
>
> ```
> A: 합계를 읽고  →  "여유 있다" 판단  →  자기 몫을 추가
> B: 합계를 읽고  →  "여유 있다" 판단  →  자기 몫을 추가
> 각자의 판단은 맞았지만 둘을 합치면 규칙이 깨진다
> ```
>
> 이걸 **write skew** 라고 부릅니다. 서로 다른 행을 쓰기 때문에 충돌이 감지되지 않고,
> **표준이 정의한 3가지 이상현상에 해당하지 않습니다.** 그래서 REPEATABLE READ로도 막히지
> 않습니다. 이론상 SERIALIZABLE에서만 막힙니다.
>
> 격리수준 표를 외우는 것만으로는 이 문제를 못 잡는다는 걸 여기서 알았습니다.

# 5. 왜 안 막히는지 — 진짜 이유

원인은 결국 두 가지였습니다.

**첫째, 요청마다 트랜잭션이 따로 만들어집니다.** (3장에서 확인)

**둘째, 사용량 합산이 일반 `SELECT` 라 락을 걸지 않습니다.**

> **배운 것 — 읽기에는 두 종류가 있습니다**
>
> | 문법 | 뜻 | 락 |
> | --- | --- | --- |
> | `SELECT ...` | 그냥 볼게 | **없음** |
> | `SELECT ... FOR SHARE` | 읽는 동안 못 바꾸게 | S락 (공유) |
> | `SELECT ... FOR UPDATE` | 내가 바꿀 거야 | X락 (배타) |
>
> InnoDB는 **읽기가 쓰기를 막지 않도록** 일반 조회에 락 대신 **MVCC 스냅샷**을 씁니다.
> 각 트랜잭션은 자기 시점의 스냅샷을 볼 뿐이라 **상대가 아직 커밋하지 않은 예약은 보이지
> 않습니다.** 그리고 락이 없으니 **서로를 기다리게 만들 수단도 없습니다.**
>
> S락과 X락의 관계도 여기서 정리했습니다.
>
> ```
>         잡으려는 락
>         S락    X락
> 기존 S락 ✅    ❌
> 기존 X락 ❌    ❌
> ```
>
> S락끼리는 공존합니다. X락은 하나뿐이라 "배타적"이라고 부릅니다.
> 그리고 **일반 SELECT는 이 표 밖입니다.** X락이 걸린 행도 그냥 읽습니다.

정리하면 이렇습니다.

```
확인(check)한 값을 믿고 행동(act)하는데
그 둘이 하나로 묶여 있지 않아 사이에 다른 요청이 끼어든다
```

**check-then-act 경쟁 조건**입니다.

# 6. 어떻게 막을 것인가 — 대안을 늘어놓기

문제가 **확인과 예약 사이의 틈**이라면 손댈 곳도 그 틈뿐입니다. 막거나, 없애거나 둘 중 하나죠.

```
A. 틈을 막는다   그 사이에 아무도 들어오지 못하게 한다   (락)
B. 틈을 없앤다   확인과 예약을 한 문장으로 합친다        (원자적 UPDATE)
```

이 기준으로 검토했습니다.

| 대안 | 방식 | 판단 |
| --- | --- | --- |
| **비관적 락** | 사용자 행에 `SELECT ... FOR UPDATE` | **채택** |
| 원자적 UPDATE | `UPDATE ... WHERE used + ? <= limit` 한 문장 | 빠르지만 사용량이 컬럼과 실제 집계 두 곳에 존재하게 됨 |
| SERIALIZABLE | 일반 SELECT를 S락으로 승격 | 데드락, 필요 없는 곳까지 잠금 |
| 낙관적 락 | `@Version`으로 충돌 감지 | **적용 불가** |
| 애플리케이션 락 | `usersId`별 자바 락 | 인스턴스 1대에서만 유효 |
| 분산 락(Redis) | 인스턴스 간 조율 | 이 문제 하나로 도입하기엔 과함 |

## 낙관적 락이 왜 안 되는지

이게 의외였습니다.

> **배운 것 — 낙관적 락은 "같은 행을 두 사람이 고칠 때" 쓰는 도구입니다.**
>
> ```sql
> UPDATE users SET ..., version = 6 WHERE users_id = 32 AND version = 5;
> -- 영향 행 0 → 그 사이 누가 바꿨다 → 충돌 → 재시도
> ```
>
> 그런데 우리 흐름은 `users`를 **읽기만** 합니다. 저장하는 건 `attachments`의 **새 행**이고요.
> **아무도 같은 행을 고치지 않습니다.** version이 오를 일이 없으니 **감지할 충돌 자체가
> 없습니다.**
>
> 낙관적 락은 "이 행"을 보는데 우리는 "이 사용자의 전체 합계"를 봐야 합니다. **볼 수 있는
> 단위가 안 맞았습니다.**

## SERIALIZABLE이 왜 위험한지

이론상 write skew를 막는 유일한 격리수준인데도 안 골랐습니다.

> **배운 것 — S락으로는 줄이 서지 않습니다.**
>
> SERIALIZABLE은 트랜잭션 안의 **모든 일반 SELECT**를 `LOCK IN SHARE MODE`(S락)로 승격시킵니다.
>
> ```
> A: 사용량 합산 🔒S      B: 사용량 합산 🔒S     ← S끼리는 통과. 둘 다 성공
> A: 예약 INSERT — X 요청 → B의 S락에 막혀 대기
> B: 예약 INSERT — X 요청 → A의 S락에 막혀 대기  ← 서로를 기다린다
> ```
>
> **둘 다 통과시켜 놓고 나중에 배타를 요구**하니 데드락이 납니다.
> `FOR UPDATE`는 처음부터 X락이라 애초에 둘 다 통과하는 상황이 생기지 않습니다.
>
> 그리고 격리수준은 **트랜잭션에 거는 설정**이라 "이 조회만"을 지정할 수 없습니다.
> 막고 싶은 건 사용량 합산 하나인데 `users`·`folders` 조회까지 잠깁니다.

## 원자적 UPDATE를 안 고른 이유

성능은 이쪽이 제일 좋습니다. 락 구간이 문장 하나고 합산 스캔도 사라지니까요.

다만 사용량이 **컬럼과 실제 집계 두 곳에 존재**하게 됩니다. 지금은 매번 합산하니 파일이
지워지면 값도 알아서 줄지만, 컬럼은 스스로 줄지 않습니다. 첨부 삭제·폴더 삭제·정리 배치·저장
확정 실패마다 일일이 차감해야 하고, **한 곳이라도 빠뜨리면 에러 없이 오차가 누적**됩니다.

**지금은 틀릴 수 없는 구조인데 굳이 틀릴 수 있는 상태를 새로 만들 이유가 없다**고 판단했습니다.

# 7. 비관적 락을 걸었다 — 그런데 순서가 중요했다

용량 한도가 사용자 단위이니 경합할 자원도 사용자라고 봤습니다. 마침 **용량을 확인하려면
어차피 사용자부터 조회**하므로, 그 조회를 `FOR UPDATE`로 바꾸면 됩니다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT u FROM Users u WHERE u.usersId = :usersId")
Optional<Users> findByIdForUpdate(@Param("usersId") Long usersId);
```

기존 `findById`는 그대로 두고 새 메서드를 나란히 뒀습니다. 프로필 조회처럼 락이 필요 없는
곳은 계속 기존 것을 씁니다.

## 여기서 한 번 더 막혔다

락을 걸었는데도 안 막히는 경우가 있었습니다.

> **가장 중요한 배움 — 락은 트랜잭션의 첫 DB 접근이어야 합니다.**
>
> REPEATABLE READ에서 **스냅샷은 트랜잭션이 시작될 때가 아니라 첫 "일반" 조회 시점에
> 확정**됩니다. 그리고 `FOR UPDATE`는 잠금 읽기라 스냅샷을 만들지 않고 최신 커밋본을 읽습니다.
>
> 그래서 순서가 이렇게 되면 무너집니다.
>
> ```
> ❌ folders 조회        ← 여기서 스냅샷이 확정된다 (앞 요청은 아직 커밋 전)
>    FOR UPDATE 🔒       ← 락은 잡았다. 앞 요청이 커밋할 때까지 기다린다
>    사용량 합산          ← 그런데 아까 찍힌 스냅샷을 본다. 낡은 값이다 → 뚫린다
>
> ✅ FOR UPDATE 🔒       ← 락부터 잡는다
>    folders 조회        ← 스냅샷이 락 획득 이후에 찍힌다
>    사용량 합산          ← 최신 값
> ```
>
> **락을 걸었느냐가 아니라 어디에 걸었느냐가 결과를 갈랐습니다.**
>
> 나중에 누가 조회 한 줄을 앞에 끼워 넣으면 조용히 깨지는 자리라 주석으로 남겨 뒀습니다.

# 8. 정말 막혔는지 어떻게 확인하나

같은 시나리오를 다시 돌렸습니다.

> 처음 측정에서는 값이 이상하게 컸는데, **JIT 워밍업 전이라 2~3배로 나온 것**이었습니다.
> 측정 전에 200요청을 흘려보내고 다시 쟀습니다.

| 동시 요청 | 통과 | 초과 | p95 | 락 대기 | 총 대기 |
| --- | --- | --- | --- | --- | --- |
| **2** | **1** | **0** | 44.5ms | 1 | 26ms |
| 5 | 1 | 0 | 78.2ms | 4 | 152ms |
| **10** | **1** | **0** | 153.6ms | 9 | 548ms |
| **20** | **1** | **0** | 208.6ms | 19 | 1243ms |

**전 구간에서 초과가 0이 되었습니다.**

## 운이 좋았던 건 아닐까

초과 0만으로는 *"우연히 안 걸린 것 아닌가"* 를 못 지웁니다. 락이 실제로 걸렸는지 봐야 합니다.

> **배운 것 — `performance_schema` 없이도 락 대기를 잴 수 있습니다.**
>
> 테스트 서버는 메모리가 작아 `performance-schema=OFF`라 `data_locks`를 볼 수 없었습니다.
> 대신 이걸 씁니다.
>
> ```sql
> SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_waits';   -- 락 대기 횟수(누적)
> SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_time';    -- 총 대기 시간(누적, ms)
> ```
>
> 누적값이라 **라운드 전후로 재서 증가분**을 보면 그 시나리오가 유발한 대기가 나옵니다.

결과가 이렇게 나왔습니다.

| 동시 요청 | 2 | 5 | 10 | 15 | 20 |
| --- | --- | --- | --- | --- | --- |
| 락 대기 | 1 | 4 | 9 | 14 | 19 |

**정확히 `동시 요청 수 − 1` 입니다.**

첫 요청만 기다리지 않고 나머지는 전부 기다렸다는 뜻입니다. 우연히 막힌 게 아니라 **의도대로
한 줄로 세워졌다는 증거**입니다.

## 락을 얼마나 오래 쥐고 있나 — 역산이 틀렸다

대기 시간에서 점유 시간을 거꾸로 구해보려 했습니다. 완전 직렬이면 이렇게 되니까요.

```
총 대기 = 점유시간 × (1 + 2 + … + (N−1))
```

동시 20이면 `1243 ÷ 190 ≈ 6.5ms`. 그런데 동시 2에서는 `26 ÷ 1 = 26ms`가 나옵니다.
**값이 안 맞습니다.**

> **여기서 전제가 틀렸다는 걸 알았습니다.**
>
> 이 식은 **모든 요청이 락을 똑같이 오래 쥔다**고 가정합니다. 그런데 실제로는 두 종류입니다.
>
> ```
> 통과하는 요청   합산 → 검증 통과 → URL 생성 → 예약 3건 저장 → 커밋
> 거부되는 요청   합산 → 검증 실패 → 예외                        ← 훨씬 짧다
> ```
>
> 동시 2는 대기가 1회뿐이라 **그 값이 곧 통과 요청의 점유 시간(26ms)** 입니다.
> 모두 26ms씩 쥐었다면 동시 20의 총 대기는 `26 × 190 = 4,940ms`여야 하는데 실측은 1,243ms,
> 4분의 1입니다.
>
> ```
> 통과 요청  ≈ 26ms
> 거부 요청  ≈ 5~9ms
> ```
>
> **거부 경로가 짧은 것이 이 구조를 지탱하고 있었습니다.** 뒤에 온 요청들이 저장 없이 바로
> 빠지므로 동시 요청이 늘어도 대기가 제곱으로 불어나지 않습니다.

## 느려지지 않았나

락을 걸었으니 당연히 느려졌을 거라 생각했는데, 아니었습니다.

```
p95 (동시 20)   228ms  →  209ms
```

**락 대기가 새로 생겼는데도 오히려 낮습니다.** 이전에는 10건이 전부 예약을 저장했지만 이제는
1건만 저장하고 19건은 빠르게 거부되기 때문입니다. **줄어든 일이 더 컸습니다.**

---

# 9. 정리

```
초과 135MB → 0        전 구간
p95 228 → 209ms       사실상 그대로
락 대기 = N − 1        직렬화 검증
```

**막힌 자리마다 배운 것**을 되짚으면 이렇습니다.

| 막힌 지점 | 배운 것 |
| --- | --- |
| `@Transactional`이 안 통함 | 원자성 ≠ 상호배제. 트랜잭션은 요청마다 별개 |
| 격리수준으로도 안 막힘 | 우리 문제는 write skew — 표준 3현상에 없다 |
| 왜 안 막히나 | 일반 SELECT는 락을 안 걸고 MVCC 스냅샷을 읽는다 |
| 낙관적 락 적용 불가 | 갱신하는 행이 없으면 감지할 충돌도 없다 |
| SERIALIZABLE 기각 | S락은 서로를 통과시켜 줄이 안 서고, 나중에 X락을 요구해 데드락 |
| 락을 걸었는데 안 막힘 | 스냅샷은 첫 일반 조회에 확정된다 — 락이 첫 접근이어야 한다 |
| 역산이 안 맞음 | 통과 요청과 거부 요청의 점유 시간이 다르다 |

가장 크게 남은 건 **"격리수준 표를 외우는 것과 문제를 푸는 것은 다르다"** 는 것입니다.
4개 수준과 3개 이상현상은 금방 외웠지만, 정작 우리 문제는 그 표에 없었고 원인은 `SELECT`가
락을 거느냐 마느냐에 있었습니다.

## 남은 것

- 서버를 거쳐 올리는 **구버전 업로드 경로**에는 아직 적용하지 않았습니다. 트랜잭션을 붙이면
  S3 업로드가 락 구간에 들어가므로 별도 설계가 필요합니다.
- 업로드 크기를 **클라이언트가 보낸 값으로 신뢰**하고 있습니다. 저장 확정에서 `HeadObject`로
  실측해야 집계가 S3와 일치합니다.
- SERIALIZABLE을 **실제로 적용해 데드락 빈도와 지연을 재는 것**은 아직 하지 않았습니다.
  논증으로 기각했는데, 숫자로 확인해 두려 합니다.
