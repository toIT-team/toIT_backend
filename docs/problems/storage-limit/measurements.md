# 측정 기록 — 스토리지 용량 제한

## 환경

| 항목 | 값 |
|---|---|
| 서버 | 테스트 서버 (AWS Lightsail, 2 vCPU / 2GB) |
| DB | MySQL 8.0 (`innodb-buffer-pool-size=256M`, `performance-schema=OFF`) |
| 앱 | Spring Boot 3.5.9 / Java 21, `-Xms256m -Xmx512m` |
| HikariCP | **기본값** (`maximum-pool-size=10`, 별도 설정 없음) |
| 격리수준 | MySQL 기본 **REPEATABLE READ**, `presignUpload` 에 `@Transactional` 적용 |
| 대상 | `users_id=32`, `folders_id=4096` |
| 부하 도구 | k6 (`per-vu-iterations`, VU 당 1회) |
| 경로 | `http://localhost:8080` — **NGINX Rate Limiter 우회** |

> Rate Limiter(`limit_req`, burst=20 + nodelay)를 거치면 요청이 잘려
> 애플리케이션 레벨 동시성을 측정할 수 없다. 서버 내부에서 앱 포트로 직접 보냈다.

스크립트: `docs/problems/storage-limit/scripts/`

## 2. 정리 배치 (2026-08-09)

presign 만 호출하고 confirm 을 보내지 않은 예약 1건.

| 시각 | 사건 |
|---|---|
| 03:33:15 | 예약 생성 (`PENDING`, 1MB) — 보관함·검색에서 안 보임, 용량은 +1MB |
| 03:43:15 | 만료 기준(10분) 도달 |
| **03:46:51** | 배치 실행 → 회수 (`s3삭제=1`, `s3실패=0`) |

```
[예약 정리] 만료 예약 1건 회수 | cutoff=2026-08-09T03:36:51 | s3삭제=1 | s3실패=0
```

회수 후 `PENDING` 0건, 용량 1MB 반환.

**소요 시간은 만료 기준(10분) + 배치 주기(5분)** 이므로 최소 10분, 최대 15분이다.
이번 건은 13분 36초 걸렸다.

> S3 에 실제 PUT 을 하지 않았는데 `s3삭제=1` 이 나왔다.
> **S3 DELETE 는 멱등이라 없는 객체를 지워도 성공으로 응답**하기 때문이다.

## 5. 비관적 락 적용 후 (2026-08-09)

`presignUpload` 의 첫 조회를 `findByIdForUpdate`(`SELECT ... FOR UPDATE`) 로 교체.
4번과 완전히 같은 조건 — 남은 용량 15MB, 요청당 15MB(이미지 3장 × 5MB), **정상 통과 기대치 1건.**

락 대기는 `SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_%'` 의 라운드 전후 증가분이다.
테스트 서버는 `performance-schema=OFF` 라 `data_locks` 를 볼 수 없다.

**워밍업 10라운드 × 동시 20 = 200요청**을 흘려보낸 뒤 측정했다.
워밍업 없이 재면 값이 2~3배로 나온다 (아래 부록 참고).

| 동시 요청 | 통과 | 차단 | 초과(MB) | p95 | 락 대기(회) | 총 대기(ms) | 평균 대기 |
|---|---|---|---|---|---|---|---|
| **2** | **1** | 1 | **0.00** | 44.50ms | 1 | 26 | 26.0 |
| 3 | 1 | 2 | 0.00 | 54.36ms | 2 | 55 | 27.5 |
| 5 | 1 | 4 | 0.00 | 78.17ms | 4 | 152 | 38.0 |
| 8 | 1 | 7 | 0.00 | 112.08ms | 7 | 382 | 54.6 |
| **10** | **1** | 9 | **0.00** | 153.58ms | 9 | 548 | 60.9 |
| 15 | 1 | 14 | 0.00 | 161.13ms | 14 | 974 | 69.6 |
| **20** | **1** | 19 | **0.00** | 208.59ms | 19 | 1243 | 65.4 |

### 관찰

**전 구간 초과 0.** 4번에서 동시 2 → 15MB, 동시 10 이상 → 135MB 였던 것이 전부 사라졌다.

**락 대기 = 동시 요청 - 1.** 첫 요청만 대기 없이 통과하고 나머지는 전부 기다렸다.
정확히 일치하므로 우연이 아니라 의도대로 직렬화된 것이다.

**락 점유 시간은 두 갈래다.**
처음에는 `총 대기 ÷ (1+2+…+N-1)` 로 역산하려 했으나, 이는 모든 요청이 락을 똑같이 오래
쥔다는 전제라 맞지 않았다. 통과 요청은 예약을 저장하고 거부 요청은 예외로 빠지기 때문이다.

동시 2 는 대기가 1회뿐이라 그 값이 곧 통과 요청의 점유 시간이다 — **26ms**.
전부 26ms 씩 쥐었다면 동시 20 의 총 대기는 `26 × 190 = 4940ms` 여야 하나 실측은 1243ms 다.

거부 요청의 점유 시간을 `h` 라 두고 `(N-1)×26 + C(N-1,2)×h = 총 대기` 로 풀면 이렇다.

| 동시 요청 | 총 대기 | 역산된 `h` |
|---|---|---|
| 3 | 55 | 3.0ms |
| 5 | 152 | 8.0ms |
| 8 | 382 | 9.5ms |
| 10 | 548 | 8.7ms |
| 15 | 974 | 6.7ms |
| 20 | 1243 | 4.4ms |

```
통과 요청  ≈ 26ms    합산 → 검증 통과 → URL 생성 → 예약 3건 저장 → 커밋
거부 요청  ≈ 5~9ms   합산 → 검증 실패 → 예외
```

`h` 가 한 값으로 수렴하지 않고 동시 요청 수가 커질수록 작아진다.
k6 가 VU 를 동시에 출발시켜도 완벽히 겹치지는 않아, 뒤쪽 요청이 앞선 요청 **전부**를
기다리지는 않기 때문으로 보인다. 그래서 단일 값이 아니라 범위로 적는다.

**거부 경로가 짧은 것이 이 구조를 지탱한다.** 뒤에 온 요청들이 저장 없이 바로 빠지므로
동시 요청이 늘어도 평균 대기가 26ms → 65ms 로만 늘고 제곱으로 불어나지 않는다.

**p95 는 사실상 그대로다.** 동시 20 에서 228ms(4번) → 209ms.
락 대기가 새로 생겼는데도 오히려 낮은 이유는, 4번에서는 10건이 전부 예약을 저장했지만
이제는 1건만 저장하고 19건은 빠르게 거부되기 때문이다. 줄어든 일이 더 크다.

**커넥션 풀 상한이 더는 나타나지 않는다.** 4번에서는 통과가 10(풀 크기)에서 포화했는데,
이제 통과는 항상 1이라 풀 크기와 무관하다. 다만 대기하는 요청이 커넥션을 붙잡는 것은 그대로다.

같은 코드, 같은 조건에서 워밍업만 뺐다. 초과는 동일하게 0 이지만 시간 지표가 부풀려진다.

## 6. 격리수준 SERIALIZABLE 단독 (2026-08-10)

비관적 락을 걷어내고 `@Transactional(isolation = SERIALIZABLE)` 만 적용.
5번과 같은 조건 — 남은 용량 15MB, 요청당 15MB, 워밍업 200요청.

데드락 횟수는 `information_schema.INNODB_METRICS` 의 `lock_deadlocks` 라운드 전후 증가분이다.
MySQL 8 은 `SHOW GLOBAL STATUS` 에 데드락 카운터를 노출하지 않는다.

| 동시 요청 | 통과 | 차단 | 실패 | 초과(MB) | p95 | 락 대기(회) | 데드락 |
|---|---|---|---|---|---|---|---|
| **2** | **1** | 1 | 0 | **0.00** | 53.66ms | 1 | **0** |
| 3 | 1 | 0 | 2 | 0.00 | 116.81ms | 3 | **2** |
| 5 | 1 | 0 | 4 | 0.00 | 121.90ms | 5 | **4** |
| 8 | 1 | 0 | 7 | 0.00 | 167.35ms | 8 | **7** |
| **10** | **1** | 0 | 9 | **0.00** | 209.78ms | 10 | **9** |
| 15 | 1 | 5 | 9 | 0.00 | 259.53ms | 10 | **9** |
| **20** | **1** | 10 | 9 | **0.00** | 290.86ms | 10 | **9** |

`실패` 는 200 도 400 도 아닌 응답이다. 데드락은 500 으로 떨어지므로 여기 잡힌다.

### 관찰

**초과는 0 이다.** SERIALIZABLE 도 write skew 를 막는다. 정확성만 보면 비관적 락과 같다.

**락 대기 = N, 데드락 = N − 1, 통과 = 1.** 예상한 메커니즘과 정확히 일치한다.

```
N 개 전부 S 락 획득           → 아무도 안 기다린다 (S 끼리 호환)
N 개 전부 INSERT 용 X 락 요구  → 서로의 S 락에 막힌다 (락 대기 N)
InnoDB 가 N-1 개를 희생자로 골라 롤백   (데드락 N-1)
살아남은 1 개만 커밋                    (통과 1)
```

**동시 10 에서 포화한다.** 데드락이 15, 20 에서도 9 로 고정이다.
커넥션 풀(10)이 여기서도 상한을 정한다. 풀 밖 요청은 대기하다가 앞선 예약이 커밋된 것을 보고
정상 차단된다 — 동시 15 에서 차단 5, 동시 20 에서 차단 10.

**동시 2 는 데드락이 나지 않는다.** 차단 1 로 정상 처리된다.
k6 가 동시에 출발시켜도 2 개로는 실제로 겹치지 않아, 한쪽이 먼저 완주하면
다른 쪽은 최신 값을 보고 거부된다. **동시성이 낮으면 데드락 조건 자체가 성립하지 않는다.**

**p95 는 비관적 락보다 높다.** 동시 20 에서 209ms(5번) → 291ms, 39% 증가.

## 7. 비관적 락 + SERIALIZABLE (2026-08-10)

6번을 재기 전에 실수로 먼저 측정한 조합이다. 비관적 락을 남긴 채 격리수준만 올렸다.

| 동시 요청 | 통과 | 차단 | 실패 | 초과(MB) | p95 | 락 대기(회) | 데드락 |
|---|---|---|---|---|---|---|---|
| 2 | 1 | 1 | 0 | 0.00 | 61.14ms | 1 | 0 |
| 3 | 1 | 2 | 0 | 0.00 | 100.03ms | 2 | 0 |
| 5 | 1 | 4 | 0 | 0.00 | 117.55ms | 4 | 0 |
| 8 | 1 | 7 | 0 | 0.00 | 144.71ms | 7 | 0 |
| 10 | 1 | 9 | 0 | 0.00 | 154.38ms | 9 | 0 |
| 15 | 1 | 14 | 0 | 0.00 | 213.13ms | 14 | 0 |
| **20** | **1** | 19 | 0 | **0.00** | **296.11ms** | 19 | **0** |

### 관찰

**데드락이 0 이다.** `SELECT ... FOR UPDATE` 가 트랜잭션의 첫 문장이라 거기서 X 락이 잡히고,
뒤에 온 요청은 SUM 에 도달하기도 전에 멈춘다. 둘 다 S 락을 쥐는 상황이 생기지 않으므로
데드락 조건이 성립하지 않는다.

**p95 만 오른다.** 동시 20 에서 209ms(비관적 락만) → 296ms, 42% 증가.
초과 0, 데드락 0 으로 결과는 같은데 비용만 늘었다.

**이미 락으로 직렬화하고 있으면 격리수준을 올려도 얻는 것이 없다.**

## 8. 비관적 락 재측정 — 대기 시간과 재현성 (2026-08-11)

5번과 같은 코드·같은 조건으로 다시 쟀다. 목적이 두 가지였다.

```
① 기다린 요청들이 타임아웃이나 데드락으로 실패하지는 않았는지
② 락 대기가 실제로 얼마나 되는지
```

측정 항목에 **최장 응답**(k6 `http_req_duration` 의 `max`)을 추가했다.
단일 최장 락 대기를 DB 에서 직접 보려고 `Innodb_row_lock_time_max` 도 넣었으나,
**서버 기동 이후 최댓값이라 워밍업 값(671ms)이 남고 `FLUSH STATUS` 로도 초기화되지 않았다.**
그래서 라운드별 값을 얻지 못했고, 대신 최장 응답으로 상한을 잡았다.

| 동시 요청 | 통과 | 차단 | 실패 | 초과(MB) | p95 | 최장 응답 | 락 대기(회) | 대기 합계 | 평균 대기 | 데드락 |
|---|---|---|---|---|---|---|---|---|---|---|
| **2** | **1** | 1 | 0 | **0.00** | 56.20ms | 56.53ms | 1 | 32 | 32.0 | **0** |
| 3 | 1 | 2 | 0 | 0.00 | 50.85ms | 51.25ms | 2 | 55 | 27.5 | **0** |
| 5 | 1 | 4 | 0 | 0.00 | 56.78ms | 57.34ms | 4 | 115 | 28.8 | **0** |
| 8 | 1 | 7 | 0 | 0.00 | 83.27ms | 84.76ms | 7 | 279 | 39.9 | **0** |
| **10** | **1** | 9 | 0 | **0.00** | 138.26ms | 140.45ms | 9 | 748 | 83.1 | **0** |
| 15 | 1 | 14 | 0 | 0.00 | 230.54ms | 237.55ms | 14 | 1185 | 84.6 | **0** |
| **20** | **1** | 19 | 0 | **0.00** | 161.74ms | 164.02ms | 19 | 910 | 47.9 | **0** |

### 관찰

**기다린 요청은 하나도 죽지 않았다.** 전 구간에서 `통과 + 차단 = 동시 요청 수` 이고 실패 0,
데드락 0 이다. 차단은 400 "스토리지 용량이 초과되었습니다" 로, 의도한 응답이다.

**락 대기 = 동시 요청 수 − 1 이 그대로 재현됐다.** 5번과 같다.

**대기 한 건당 평균 28~85ms.** 요청 하나를 처리하는 시간과 같은 수준이라 앞선 요청이
커밋하는 즉시 넘겨받았다.

**최장 응답이 p95 와 1~3% 차이다.** 보통 최장은 p95 보다 몇 배 크다. 거의 붙어 있다는 것은
유난히 오래 기다린 요청이 없었다는 뜻이다. 동시 20 의 최장 응답 164ms 안에 락 대기가
포함되므로 **어떤 요청도 164ms 보다 오래 기다리지 않았다.** `innodb_lock_wait_timeout` 이
50초이므로 0.3% 수준이다.

**동시 20 이 15 보다 낮게 나왔다** (910ms vs 1185ms). 5번에서는 반대였다(1243 vs 974).
구조적 결과가 아니라 측정 편차다.

### 응답 시간 절대값은 신뢰할 수 없다

같은 코드로 세 번 측정했을 때 동시 20 의 p95 가 이렇게 나왔다.

| 회차 | 동시 2 | 동시 10 | 동시 20 |
|---|---|---|---|
| 1 | 76.34ms | 176.42ms | 316.75ms |
| 2 | 52.71ms | 138.53ms | 256.27ms |
| 3 | 56.20ms | 138.26ms | 161.74ms |

**동시 20 에서 162~317ms, 약 2배 차이다.** 2 vCPU 테스트 서버라 편차가 크다.

그래서 **개선 전후 응답 시간 비교는 하지 않기로 했다.** 이전에 문서에 적었던
`p95 228ms → 209ms` 는 서로 다른 시점의 단발 측정을 나란히 놓은 것이라 근거가 되지 않는다.

반면 아래 값들은 세 번 모두 같았다.

```
통과 1 · 차단 N−1 · 실패 0 · 데드락 0 · 초과 0
락 대기 = N − 1
최장 응답 ≈ p95 (1~3%)
```

**구조가 정하는 값은 재현되고, 타이밍이 정하는 값은 흔들린다.**
근거로 쓸 것은 앞쪽이다.

## 방법 비교

| | 초과(동시 20) | 통과(동시 20) | 데드락 | 사용자가 받는 응답 |
|---|---|---|---|---|
| 개선 전 (락 없음, REPEATABLE READ) | **135MB** | 10 | 0 | 200 — 잘못 통과 |
| **비관적 락** | **0** | **1** | 0 | **400 용량 초과** |
| SERIALIZABLE | 0 | 1 | **9** | **500 서버 오류** |
| 비관적 락 + SERIALIZABLE | 0 | 1 | 0 | 400 |

p95 는 비교 항목에서 뺐다. 8번에서 확인했듯 같은 코드로도 실행마다 2배 가까이 흔들려서
방법 간 비교에 쓸 수 없다.

정확성은 세 방법 모두 같다. 차이는 **사용자가 무엇을 받는가**다.
SERIALIZABLE 은 동시 10 에서 10건 중 9건이 500 을 받는다.
용량이 초과되었다는 사실을 알 수 없고, 재시도해도 또 데드락이 날 수 있다.

## 측정하며 겪은 것

**토큰 만료를 결과로 착각할 뻔했다.** 6번을 처음 돌렸을 때 전 구간에서
통과 0 / 차단 0 / 실패 = 동시 요청 수, 초과 −15MB 가 나왔다.
SERIALIZABLE 문제로 보였지만 실제로는 **JWT 가 만료되어 401 을 받고 있었다.**

구분 방법은 이렇다.

| 신호 | 뜻 |
|---|---|
| 락 대기 0, 데드락 0 | DB 작업 자체가 일어나지 않았다 |
| p95 가 수십 ms 로 짧다 | 인증 단계에서 바로 튕겼다 |
| 초과가 음수 | filler 만 있고 아무것도 저장되지 않았다 |

`run_curve.sh` 가 k6 출력을 삼켜서 상태코드가 안 보였다.
이상하면 `race.js` 를 직접 돌려 `console.error` 로 찍히는 상태코드를 먼저 확인한다.
