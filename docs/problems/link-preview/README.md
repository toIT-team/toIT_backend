# 03. 링크 프리뷰 외부 호출의 스레드 점유와 SSRF

> **축** 격리 · 보안 | **우선순위** 3 | **상태** 미착수
> 이미 `blog/링크-프리뷰-*.md` 를 쓴 기능. **각도만 바꾸면** 적은 비용으로 축이 하나 늘어납니다.

---

## 1. 왜 각도를 바꾸는가

기존 두 글은 **"로컬과 운영의 응답이 다르다"** 는 환경 차이 디버깅입니다.
읽는 재미는 있지만 면접에서 "그래서 무엇을 설계했나요"에 답하기 어렵습니다.

같은 기능을 **"외부 의존 호출을 어떻게 격리하는가"** 로 보면 설계 이야기가 됩니다.
그리고 현재 포트폴리오에 **보안 항목이 하나도 없는데**, 여기에 SSRF가 자연스럽게 붙습니다.

> 참고: 이 기능의 코드 품질과 주석은 이미 좋습니다.
> UA 사칭의 한계를 스스로 적어둔 부분(`JsoupLinkPreviewStrategy.java:64-68`)처럼
> 트레이드오프를 인지한 서술이 이미 있습니다. 없는 건 **격리와 보안 관점**입니다.

## 3. 무엇이 문제인가

### 3-1. 타임아웃이 누적된다

`JsoupLinkPreviewStrategy.extract()`는 UA를 바꿔가며 최대 2회 시도합니다.

```java
for (int i = 0; i < USER_AGENTS.size(); i++) {
    Attempt attempt = tryExtract(url, USER_AGENTS.get(i), lastAttempt);
    if (attempt.preview() != null) return attempt.preview();
    if (!attempt.worthRetrying()) return null;
}
```

응답하지 않는 서버를 만나면:

```
Jsoup 1차 (UA: facebookexternalhit)   4초
Jsoup 2차 (UA: Chrome)                4초
oEmbed 발견 시 추가                   3초
────────────────────────────────────────
                              최대 약 11초
```

**개별 타임아웃은 짧은데 총 소요는 10초를 넘길 수 있습니다.**
"타임아웃을 걸었으니 안전하다"가 성립하지 않는 전형적인 사례입니다.

### 3-2. 그동안 톰캣 스레드가 묶인다

이 호출은 **요청 스레드에서 동기로** 실행됩니다.
느린 외부 사이트 링크를 여러 사용자가 동시에 저장하면 톰캣 워커 스레드가 그만큼 점유됩니다.

운영 환경은 **2 vCPU / 2GB LightSail 단일 인스턴스**입니다.
톰캣 기본 `max-threads`가 200이라 해도, 스레드가 외부 응답을 기다리는 동안:

- 다른 API(검색, 목록 조회)의 처리 여력이 줄어든다
- 이미 측정한 검색 용량(동시 50명)이 링크 프리뷰 트래픽에 의해 잠식된다
- **내 서버가 멀쩡해도 외부 사이트 때문에 느려진다**

> 정재익님 포트폴리오의 "LLM 호출이 HikariCP·톰캣 스레드풀을 점유하는 문제"와 같은 클래스입니다.

### 3-3. SSRF 방어가 없다

`LinkPreviewExtractor.java:55`

```java
if (!u.startsWith("http://") && !u.startsWith("https://")) {
    u = "https://" + u;
}
```

**스킴 검사만 있고 대상 주소 검증이 없습니다.**
사용자가 준 URL로 서버가 직접 HTTP 요청을 보내는 구조이므로 교과서적인 SSRF입니다.

공격 가능한 대상:

| 대상 | 예시 | 위험 |
|---|---|---|
| 클라우드 메타데이터 | `http://169.254.169.254/latest/meta-data/` | **IAM 자격증명 탈취 가능** |
| 루프백 | `http://127.0.0.1:8080/actuator/` | 내부 엔드포인트 접근 |
| 사설 대역 | `http://10.0.0.x`, `http://192.168.x.x` | 내부망 스캔 |
| 컨테이너 내부 | `http://postgres:5432` | Docker 네트워크 내 서비스 |

게다가 `followRedirects(true)`(`JsoupLinkPreviewStrategy.java:126`)이므로,
**외부 도메인이 내부 주소로 리다이렉트하면 최초 URL만 검사해서는 막을 수 없습니다.**

응답 본문이 그대로 title/description에 담겨 반환되므로 **결과가 사용자에게 노출**됩니다.

## 4. 재현 계획

### 4-1. 스레드 점유

| 시나리오 | 방법 | 확인할 것 |
|---|---|---|
| 기준선 | 정상 링크로 프리뷰 요청 | 응답 시간 p50/p95 |
| 지연 주입 | 응답하지 않는 테스트 서버 URL | **실제 최대 소요 시간**(11초 가정 검증) |
| 스레드 고갈 | 지연 URL로 동시 50/100 요청 | 톰캣 활성 스레드 수, **동시 실행 중인 검색 API의 응답 저하** |

핵심 측정은 마지막입니다. **링크 프리뷰 부하가 검색 API의 SLO를 깨뜨리는지**를 보여야
"격리가 필요하다"는 근거가 됩니다. 기존 검색 SLO(700ms 95%) 측정 자산을 그대로 씁니다.

### 4-2. SSRF

로컬/스테이징에서만 확인하고 **운영에서는 절대 시도하지 마세요.**

- `http://127.0.0.1:<포트>/actuator/health` → 응답이 프리뷰에 담기는가
- 외부 도메인 → 내부 주소로 302 리다이렉트 → 우회되는가
- `http://[::1]/`, `http://2130706433/`(정수 표기) 등 우회 표기

## 5. 고려할 대안

### 5-1. 스레드 격리

| 대안 | 트레이드오프 |
|---|---|
| **전체 타임아웃(budget) 도입** | 개별이 아닌 **합계 상한**을 두어 3-1 해결. 가장 저렴. 다만 스레드 점유 자체는 남음 |
| **전용 스레드 풀로 분리** | 프리뷰가 다른 API의 스레드를 잠식하지 못하게 함(벌크헤드). 풀 크기·거부 정책 설계 필요 |
| **비동기 + 폴링** | 저장은 즉시, 프리뷰는 나중에 채움. UX 변경 필요 |
| **서킷 브레이커** | 특정 도메인이 반복 실패하면 일정 시간 차단. 도메인 단위 상태 관리 필요 |
| **프리뷰 캐싱** | 같은 URL 재요청 시 외부 호출 자체를 제거. 캐시 무효화 정책 필요 |

> **벌크헤드 패턴**이 핵심 개념입니다. 배의 격벽처럼, 한 구획이 침수돼도 배 전체가 가라앉지 않게 하는 것.
> 이미 Rate Limiter로 "앞단에서 막는다"를 했으니, "안에서 구획을 나눈다"가 자연스러운 다음 단계입니다.

### 5-2. SSRF 방어

| 대안 | 트레이드오프 |
|---|---|
| **DNS 해석 후 IP 대역 검사** | 사설·루프백·링크로컬(`169.254.0.0/16`) 차단. **리다이렉트마다 재검사 필요** |
| **리다이렉트 수동 처리** | `followRedirects(false)` 후 홉마다 검증. 구현 복잡도 증가 |
| **아웃바운드 프록시 경유** | 네트워크 레벨에서 차단. 인프라 추가 |
| **IMDSv2 강제** | 메타데이터 탈취 방어(토큰 필수화). AWS 설정으로 해결, **비용 대비 효과 가장 큼** |

> DNS rebinding(검사 시점과 접속 시점의 IP가 다름) 문제까지 언급하면 깊이가 드러납니다.

## 6. 파고들 지점

- **네트워크** — DNS 해석, 사설 IP 대역(RFC 1918), 링크로컬(RFC 3927), 리다이렉트 체인
- **보안** — SSRF, DNS rebinding, 클라우드 메타데이터 서비스, IMDSv1 vs v2
- **격리 패턴** — 벌크헤드, 서킷 브레이커, 타임아웃 버짓
- **스레드** — 톰캣 커넥터 모델, 블로킹 I/O 대기 시 스레드 상태, 풀 분리
- **Ecole 42 연결** — IRC 서버를 만들 때 소켓 블로킹과 논블로킹을 다뤘던 경험이
  "외부 I/O가 스레드를 어떻게 묶는가"의 밑단입니다
