## 한계 찾기 — 건수를 올려가며

알림 건수를 늘려가며 **한 번의 실행이 1분을 넘기는 지점**을 찾는다. 스케줄러는
단일 스레드로 하나씩 보내므로, 1분을 넘기면 다음 실행이 제때 못 뜨고 밀린다.

`01_setup.sql` 의 `@COUNT` 만 바꿔가며 같은 순서로 돌린다.

| 건수 | 처리 시간 | 1건 중앙값 | p95 | RPS | QPS | TPS | 건당 쿼리 | 건당 읽은행 |
|---|---|---|---|---|---|---|---|---|
| 100 | 34.2 초 | 318 ms | 464 ms | 2.9 | 68 | 56 | 23.3 | 66.8 |
| **200** | **69.1 초** | 299 ms | 765 ms | **2.9** | **67** | **55** | 23.2 | 118.9 |
| **300** | **103.3 초** | 294 ms | 875 ms | **2.9** | **68** | **55** | 23.3 | 169.8 |
| **500** | **182.5 초** | 320 ms | 841 ms | **2.7** | **63** | **52** | 23.2 | 288.5 |

> `QPS`·`TPS` 는 스냅샷 차이를 **실제 발송 시간**으로 나눈 값이다. 스크립트가
> 보여주는 값은 스냅샷 사이(124.8 · 188.0 · 226.9초)로 나눈 것이라 창 길이에 따라
> 달라진다. 창에는 알림 시각을 기다린 시간이 절반 넘게 들어 있다.

## 한계는 165 ~ 175건

세 라운드가 거의 같은 값을 준다.

```
200건 ÷ 69.1초  = 2.89 건/초   × 60 = 174건
300건 ÷ 103.3초 = 2.90 건/초   × 60 = 174건
500건 ÷ 182.5초 = 2.74 건/초   × 60 = 164건
```

```
165 ~ 175건까지    한 실행이 1분 안에 끝난다
그보다 많으면       다음 실행이 제때 못 뜨고 밀린다
```

500건에서 6% 떨어졌다. 오차일 수도 있으나 **커질수록 아주 조금씩 나빠지는
방향**이다.

### 처리량은 안 꺾였다

건수를 3배로 늘려도 **초당 처리량이 2.9 로 그대로다.** 단일 스레드로 하나씩
보내므로 자원이 포화되는 지점이 아직 안 나왔다.

그래서 여기서 말하는 한계는 **"처리량이 꺾이는 곳" 이 아니라 "한 실행이 1분을
넘기는 건수"** 다.

### 100건은 세 번 쟀다

| 회차 | 처리 시간 | 중앙값 | p95 | 건당 쿼리 |
|---|---|---|---|---|
| 1회 | **34.2 초** | 318 ms | 464 ms | 23.3 |
| 2회 | 37.6 초 | 330 ms | 600 ms | — |
| 3회 | 46.2 초 | 346 ms | 895 ms | 16.4 |

**34 ~ 46초로 흔들렸다.** 위 표에는 **가장 빠른 1회차**를 실었다. 개선 전 값이
느릴수록 나중에 개선이 커 보이므로, **개선 전에는 가장 유리한 값을 쓰는 것**이
공정하다.

그리고 1회차가 다른 건수와도 맞는다. `건당 쿼리` 가 23.3 으로 200·300·500 의
23.2 · 23.3 · 23.2 와 같고, `QPS` 68 도 67 · 68 · 63 과 같은 줄이다. 3회차만
16.4 · 35 로 혼자 떨어져 있다.

**한 번 재고 결론 내리면 안 된다**는 것이 이 표의 소득이다.

### 읽은 행이 건수의 제곱으로 늘어난다

```
건수    건당 읽은행    전체 읽은 행    ÷ 건수²
100       66.8         6,680       0.67
200      118.9        23,780       0.59
300      169.8        50,940       0.57
500      288.5       144,250       0.58
```

**네 지점이 0.57 ~ 0.67 로 모인다.** 우연이 아니라 `N²` 에 비례한다.

`N²/2` 는 **"실행 중에 1행씩 커지는 테이블을 매 건마다 훑는"** 모양이다.
1 + 2 + ... + N 이기 때문이다.

건당 쿼리는 23 으로 고정인데 **읽은 행만 는다.** 쓰기 쪽은 정확하다.

```
넣은 행    501    알림함 500 + 스냅샷 1
고친 행   1001    예약 500 + 알림함 500
```

**인덱스를 넣고 다시 재도 안 줄었다.** 개선 후 500건에서 285.5 로, 개선 전 288.5
와 사실상 같다. `EXPLAIN` 은 `type=range` 에 `idx_alarm_pending` 을 쓰고 있으니
인덱스는 제대로 걸렸다. 스케줄러 조회가 원인이 아니었다는 뜻이다.

알림을 하나도 안 보내는 구간으로도 재봤다.

```
304.7초 유휴    쿼리 57   읽은 행 12,900    초당 42행
27.7초 유휴     쿼리 13   읽은 행 1,050     초당 38행
```

**유휴에서도 초당 40행쯤 읽는다.** 다만 500건 실행의 창(330.7초)에 대면 13,200행
으로 전체의 9% 밖에 안 되어, 배경 활동 탓도 아니다.

유휴 한 틱이 쿼리 11개에 2,580행을 읽는데, 스케줄러 조회는 그중 하나뿐이다.
나머지가 어디서 오는지는 **아직 모른다.** `users_settings` 조인을 의심했으나 그
테이블은 두 행뿐이라 아니었다.

지금 규모에서 문제가 되는 값은 아니라 여기까지 적어두고 넘어간다.

인덱스로 콕 집어 읽는다면 **건당 읽은 행은 건수와 무관하게 일정해야** 한다. 늘어난다는
것은 알림 하나를 처리할 때마다 **데이터가 많아진 만큼 더 읽고 있다**는 뜻이고,
어딘가에 스캔이 있다는 신호다.

### 스케줄러 조회가 전체 스캔이었다

`EXPLAIN` 으로 확인한 결과다.

```
fcm_token        type=ref    FK 인덱스     rows=1     정상
users_settings   type=const  유니크 키     rows=1     정상
schedules_alarm  type=ALL    key 없음                 전체 스캔
```

`SHOW INDEX FROM schedules_alarm` 을 보면 인덱스가 둘뿐이다.

```
PRIMARY                       schedules_alarm_id
UKml5ta1grdso2f1n7dfq4nr2j0   schedules_id
```

**`alarm_date_time` 에도 `is_sent` 에도 인덱스가 없다.** 스케줄러가 1분마다
`schedules_alarm` 을 통째로 읽는다. 지금은 예약이 적어 티가 안 나지만, 지난 알림도
계속 남으므로 서비스가 오래될수록 스캔이 커진다.

```sql
CREATE INDEX idx_alarm_pending ON schedules_alarm (status, alarm_date_time);
```

등호 조건(`status`)이 앞, 범위 조건(`alarm_date_time`)이 뒤여야 인덱스를 끝까지
탄다.

### 100건을 세 번 돌려보니

| 회차 | 처리 시간 | 중앙값 | p95 |
|---|---|---|---|
| 1회 | 34.2 초 | 318 ms | 464 ms |
| 2회 | 37.6 초 | 330 ms | 600 ms |
| 3회 | **46.2 초** | 346 ms | **895 ms** |

**중앙값은 ±4% 로 안정적인데 p95 는 두 배 차이가 난다.** 느린 건이 몇 개 섞이면
전체 시간이 그만큼 늘어나, 처리 시간도 34~46초로 흔들린다.

그래서 **개선 전후를 비교할 때 처리 시간 하나로 판단하면 안 된다.** 중앙값을
같이 봐야 한다.

### 아직 모르는 것

```
읽은 행이 왜 느는지   전체 스캔은 실행당 1회라 건당으로는 상수여야 한다.
                   이것만으로는 설명이 안 된다
더 큰 규모          500 · 1000 에서도 RPS 2.9 가 유지되는지
```

**인덱스를 넣고 다시 재면 갈린다.** 인덱스 때문이면 확 줄고, 아니면 그대로일 것이다.

### 구간을 쪼개면

`건너뜀` 로그는 토큰 목록이 비어 반환하는 자리에 찍히는데, **그 지점이 곧 FCM 호출
직전**이다. 토큰을 지운 실행을 그 구간의 값으로 쓸 수 있다.

```
발송시도
  │  알림함 INSERT · 설정 조회 · 토큰 조회      29 ms      토큰 없는 실행
  ├─ FCM 직전
  │  FCM 왕복                                289 ms     318 − 29
  ├─ 전송성공
  │  알림함 발송표시 · 예약 완료표시             21 ms      339 − 318
  └─ 완료표시                                339 ms
```

```
FCM 왕복    289 / 339 = 85%
DB 합계      50 / 339 = 15%
```

**시간의 85% 가 FCM 왕복이다.** 배치 발송(`sendEach`)이 처리량 개선의 유일한 큰
수라는 근거가 여기서 나온다. 지연 로딩을 고쳐도 나머지 15% 안에서 움직인다.

토큰을 지운 실행은 FCM 을 아예 안 타므로 **「FCM 제외」 상한선**이기도 하다.

```
FCM 포함    초당 2.9 건    분당 175 건
FCM 제외    초당 25 건     분당 약 1,500 건      100건 3.99초
```

**FCM 왕복이 처리량을 9배 떨어뜨린다.**

### 실패했을 때 `(n=1, 다시 측정 필요)`

| 상황 | 시각 | 소요 |
|---|---|---|
| 실패 (SENDER_ID_MISMATCH) | `23:50:00.073` → `23:50:01.578` | 1,505 ms |
| 실패 (THIRD_PARTY_AUTH_ERROR) | `01:30:00.041` → `01:30:03.028` | 2,987 ms |

**둘 다 한 건씩만 잰 값이다.** 토큰을 지운 실행은 `건너뜀`(FCM 미호출)이고 위
실험은 전부 성공이라 **진짜 실패 케이스가 비어 있다.** `UNAVAILABLE` 같은 응답을
만들려면 가짜 FCM 이 필요하다.

## 개선 후 — 건수별 재측정

`07_migrate.sql` 로 컬럼과 인덱스를 넣고 재처리 구조를 배포한 뒤, 개선 전과 같은
방법으로 네 지점을 다시 돌렸다.

| 건수 | 처리 시간 | 1건 중앙값 | p95 | RPS | QPS | TPS | 건당 쿼리 | 건당 읽은행 |
|---|---|---|---|---|---|---|---|---|
| 100 | 36.3 초 | 332 ms | 508 ms | 2.8 | 68 | 56 | 24.7 | 152.4 |
| 200 | 71.9 초 | 341 ms | 443 ms | 2.8 | 67 | 56 | 24.2 | 158.3 |
| 300 | 103.6 초 | 330 ms | 400 ms | 2.9 | 70 | 58 | 24.1 | 168.5 |
| 500 | 199.3 초 | 295 ms | 869 ms | 2.5 | 61 | 50 | 24.2 | 285.5 |

### 속도는 사실상 같다

| 건수 | 처리 시간 | 1건 중앙값 | RPS |
|---|---|---|---|
| 100 | 34.2 → 36.3 초 | 318 → 332 ms | 2.9 → 2.8 |
| 200 | 69.1 → 71.9 초 | 299 → 341 ms | 2.9 → 2.8 |
| 300 | 103.3 → 103.6 초 | 294 → 330 ms | 2.9 → 2.9 |
| 500 | 182.5 → 199.3 초 | 320 → 295 ms | 2.7 → 2.5 |

**빨라지지 않았다.** 200 과 500 은 오히려 조금 느려졌고 300 은 같다.
`RPS × 60` 으로 본 한계도 개선 전 164~174건, 개선 후 150~174건으로 그대로다.

시간의 85% 가 FCM 왕복이므로 **DB 쪽을 고쳐도 전체는 안 움직인다**는 예상 그대로다.

**100건도 34.2 → 36.3초로 조금 느려졌다.** 개선 전 세 회차 중 가장 빠른 값을
기준으로 삼았기 때문이다. 가장 느린 46.2 와 견주면 개선처럼 보이지만, 그건 비교
기준을 유리하게 고른 것이다.

### p95 는 좁아졌다

```
100건   895 → 508 ms
200건   765 → 443 ms
300건   875 → 400 ms
500건   841 → 869 ms      ← 여기만 그대로
```

**세 지점에서 절반 가까이 줄었다.** 느린 꼬리가 짧아졌다는 뜻이다. 다만 500 에서는
안 줄어서 **인덱스 덕인지 그날 상태인지는 단정하기 어렵다.** FCM 응답 편차가 큰
값이라 더 재봐야 갈린다.

### 상태는 네 라운드 모두 제대로 갔다

| 건수 | 발송됨 | 대기중 | 포기 | 재시도한 건수 | 알림함 | 유실 |
|---|---|---|---|---|---|---|
| 100 | 100 | 0 | 0 | 0 | 100 | 0 |
| 200 | 200 | 0 | 0 | 0 | 200 | 0 |
| 300 | 300 | 0 | 0 | 0 | 300 | 0 |
| 500 | 500 | 0 | 0 | 0 | 500 | 0 |

**전부 한 번에 성공했고 재시도가 한 번도 안 일어났다.** `last_error_code` 도 비어
있다. 알림함 줄 수가 알림 건수와 같아 **멱등키가 중복을 만들지 않는 것**까지
확인됐다.

### 조회는 인덱스를 탄다

```
개선 전    type=ALL     key 없음
개선 후    type=range   key=idx_alarm_pending   Using index condition
```

매 분 `schedules_alarm` 을 통째로 읽던 것이 없어졌다. 지금은 예약이 적어 속도로는
안 드러나지만, 지난 알림이 쌓일수록 벌어지는 차이다.

### 읽은 행은 그대로다

```
건수    개선 전    개선 후
100     66.8      152.4
200    118.9      158.3
300    169.8      168.5
500    288.5      285.5
```

**인덱스를 넣었는데 안 줄었다.** 300·500 은 거의 같고 100·200 은 오히려 늘었다.
100·200 은 측정 창(220·250초)이 발송 시간(36·72초)보다 훨씬 길어 유휴 구간이
많이 섞인 탓이다.

배경 몫(초당 40행)을 빼고 다시 계산해도 건당 64 → 108 → 134 → 259 로 여전히 는다.
**건수의 제곱에 비례하는 성질이 인덱스와 무관하게 남아 있다.**

## 스크립트

`is_sent` 를 `status` 로 바꾸면서 데이터를 만들고 세는 방법이 달라져 두 벌로 나눴다.

```
before/    개선 전.  is_sent 기준
after/     개선 후.  status · attempt_count · next_attempt_at 기준

04 · 05 · 06     양쪽 공용
```

**한 라운드**

```
1  04_teardown.sql        앞 라운드 정리
2  <폴더>/01_setup.sql     @COUNT 를 맞추고 실행
3  <폴더>/02_reset.sql     @AFTER_MIN 으로 실험 선택
4  05_metrics.sql         실험 전 스냅샷
5  대기
6  05_metrics.sql         QPS · TPS · 건당 쿼리
7  <폴더>/03_count.sql     도달 건수
8  docker compose logs app --since 30m > app.log
   python3 06_latency.py app.log
```

쓰는 법은 [scripts/README.md](scripts/README.md) 에 두었다.

## 실험 A — 서버가 꺼진 사이

**절차**

```
1  docker compose stop app
2  reset.sql 로 알림 시각을 NOW() 로 옮긴다
3  2분 대기
4  docker compose start app
5  로그와 DB 를 5분간 관찰
```

**개선 전** — 2026-08-25 측정

알림 시각을 `17:03:41` 로 맞춘 뒤 서버를 껐고, 그 분이 지난 다음 다시 켰다.

| 항목 | 값 |
|---|---|
| 도달 | **0 / 100** |
| `is_sent = false` 로 남은 건수 | **100** |
| 울릴 시각이 지났는데 미발송 | **100** |
| 알림함에 만들어진 줄 | **0** |
| 이후 실행에서 재조회된 건수 | **0** |

로그는 재시작 이후 계속 `count=0` 이었다.

```
[ALARM] 조회 window=2026-08-25T17:05~17:06 count=0
[ALARM] 조회 window=2026-08-25T17:06~17:07 count=0
```

**알림함 줄이 0건이라는 게 핵심이다.** 알림함은 발송을 시도하기 전에 만들어지므로,
0건이라는 것은 **스케줄러가 그 알림을 집지도 않았다**는 뜻이다. 보내려다 실패한
것이 아니라 시도 자체가 없었다.

> `SUM()` 결과가 `NULL` 로 나오는 것은 셀 행이 0개이기 때문이다. 오류가 아니다.

**개선 후** — 2026-08-29 측정

서버를 먼저 끄고 알림 시각을 `NOW()` 로 맞춘 뒤, 그 분이 지난 다음 다시 켰다.
개선 전과 같은 조건이다.

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 도달 | **0 / 100** | **100 / 100** |
| `PENDING` 으로 남은 건수 | 100 | **0** |
| 울릴 시각이 지났는데 미발송 | 100 | **0** |
| 알림함에 만들어진 줄 | 0 | **100** (전부 `sent_at` 이 참) |
| 재시도한 건수 | — | 0 |
| 100건 드레인 시간 | — | 38 초 |

**재시작 뒤 첫 실행에서 100건을 전부 집었다.** 조회가 "지금 이 1분에 울릴 것"
에서 "아직 안 보낸 것" 으로 바뀌었으므로, 서버가 꺼진 사이에 지나간 시각도
다음 실행이 회수한다.

드레인 38초는 정상 발송(36.3초)과 같은 수준이다. **밀린 것을 되살리는 데 추가
비용이 거의 없다.**

## 실험 B — 발송 실패 후 복구

**절차**

```
1  DELETE FROM fcm_token WHERE users_id = ?
2  reset.sql 로 알림 시각을 2분 뒤로 설정
3  발송 실패 확인
4  앱에서 재로그인해 토큰 복구
5  로그와 DB 를 5분간 관찰
```

**개선 전** — 2026-08-25 측정

토큰을 지운 뒤 알림 시각을 2분 뒤로 맞췄고, 발송 실패를 확인한 다음 앱에서
다시 로그인해 토큰을 복구했다.

| 항목 | 값 |
|---|---|
| 발송 시도 | **100 / 100** |
| 도달 | **0 / 100** |
| `is_sent = true` 로 바뀐 건수 | **100** |
| 알림함에 만들어진 줄 | **100** (전부 `sent_at` 이 `NULL`) |
| 토큰 복구 후 재시도된 건수 | **0** |

**한 건도 안 나갔는데 `is_sent` 는 전부 `true` 로 바뀌었다.** 로그에는
`발송실패` 가 100번 찍혀 있는데 DB 에는 "전부 보냄" 으로 기록된 것이다.

실험 A 와 비교하면 흔적이 정반대다.

| | 알림함 줄 | `is_sent` | 뜻 |
|---|---|---|---|
| A | 0 | `false` | 집지도 않았다 |
| B | 100 | `true` | 집어서 100번 다 실패했는데 완료로 적혔다 |

**둘 다 도달 0 인데 남은 기록이 반대다.** 유실에 이르는 입구가 다르다는 것이
데이터로 드러난다.

**개선 후** — 2026-08-29 측정

토큰을 지운 뒤 알림 시각을 2분 뒤로 맞췄고, 발송 실패를 확인한 다음 앱에서 다시
로그인해 토큰을 복구했다. 개선 전과 같은 조건이다.

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 도달 | **0 / 100** | **0 / 100** |
| DB 기록 | `is_sent = true` (보냄) | **`FAILED`** |
| `last_error_code` | 없음 | **`NO_TOKEN` 100** |
| 알림함 줄 | 100 (`sent_at` 이 `NULL`) | 100 (`sent_at` 이 `NULL`) |
| 토큰 복구 후 재시도 | 0 | 0 |

**도달은 그대로 0 이다.** 다만 이유가 달라졌다.

```
개선 전    한 건도 안 나갔는데 "전부 보냄" 으로 적혔다
개선 후    "보낼 토큰이 없어 접었다" 가 기록됐다
```

### 왜 되살리지 않는가

토큰을 복구해도 재시도하지 않는다. **보낼 데가 없는 것은 재시도로 풀 문제가
아니라고 봤기 때문이다.**

```
FCM 장애    기다리면 풀린다              →  재시도가 맞다
토큰 없음    기다린다고 안 생긴다          →  사용자가 앱을 열어야 생긴다
```

그리고 앱을 열면 **그때부터 새 알림은 정상으로 받는다.** 지난 알림은 유효 시간
10분(6.5)에 걸려 어차피 오래 못 간다. 놓친 것은 알림함에서 볼 수 있다.

### 그래도 개선이라고 보는 이유

1장에서 **"폰에 알림이 안 와도 어디서 끊겼는지 알 수가 없었다"** 고 했다. 그
질문에 이제 답이 나온다.

```sql
SELECT last_error_code, COUNT(*) FROM schedules_alarm
WHERE status = 'FAILED' GROUP BY last_error_code;
```

```
NO_TOKEN   100
```

**로그를 뒤지지 않고 이유가 보인다.** 개선 전에는 남아 있는 기록이 "보냄" 하나뿐
이라 셀 수조차 없었다.

## 관찰 기록

측정하면서 예상과 달랐던 것, 다시 재야 했던 것.

**896ms 는 과대평가였다.** 처음에는 로그에서 눈에 띈 한 줄을 집어 `n=1` 로 썼는데,
100건을 다 뽑으니 중앙값이 318~330ms 였다. 최대가 1,399ms 인 것을 보면 **꼬리 쪽
값을 대푯값으로 삼았던 셈**이다. 그 값에서 나온 "분당 66건" 도 실제로는 159~175건
이었다.

**토큰을 지우면 FCM 을 아예 안 탄다.** 실패를 만들려고 토큰을 지웠는데
`sendToUser` 가 토큰 목록이 비면 FCM 호출 전에 반환한다. 로그에 `건너뜀
사유=토큰없음` 만 찍히고 `전송실패` 는 없다. 실패 케이스를 만들려면 가짜 FCM 이
필요하다. 대신 이 실행이 **뜻하지 않게 「FCM 제외」 측정**이 되었다.

**`Com_*` 는 `performance_schema.global_status` 에 없었다.** `SHOW GLOBAL STATUS
LIKE 'Com_commit'` 으로는 나오는데 테이블에는 `Com_stmt_reprepare` 하나뿐이었다.
`Handler_commit` · `Innodb_rows_*` 로 바꿔서 같은 것을 봤다.

**측정 도구가 자기 측정을 오염시켰다.** `05_metrics.sql` 이 알림 건수를 세려고
이 쿼리를 돌렸다.

```sql
SET @N = (SELECT COUNT(*) FROM schedules_alarm a
          JOIN schedules s ON s.schedules_id = a.schedules_id
          WHERE s.title LIKE '유실테스트-%');
```

`schedules.title` 에 인덱스가 없어 **이 한 줄이 만 건을 훑는다.** 측정 창 안에서
도는 쿼리라 잰 값에 그대로 섞였다. 500건일 때는 1,000행 정도라 묻혔고,
**10,000건에서야 드러났다.** 규모를 키우니 도구의 결함이 보인 셈이다.
`@N` 을 손으로 적는 값으로 바꿨다.

**인덱스 효과를 못 갈랐다.** 예약 10,000건을 깔고 인덱스를 넣었다 뺐다 하며
유휴 구간의 읽은 행을 쟀는데, 두 집합이 겹쳤다.

```
인덱스 있음    1.5 · 0.0 · 0.0 · 4.8   (건당 읽은행)
인덱스 없음    1.0 · 4.3
```

측정 창이 42 ~ 206초로 들쭉날쭉해 **그 안에 스케줄러가 몇 번 도느냐가 값을 좌우**
했고, 찾으려는 차이가 그 흔들림에 묻혔다. 제대로 하려면 창을 10분 이상으로
잡거나 10만 건은 되어야 한다.

`EXPLAIN` 은 `type=ALL rows=9905` 에서 `type=range rows=1` 로 분명히 바뀌었지만,
**실제 비용 차이를 보이지 못했다.** 그래서 인덱스를 넣지 않고 9장에 남겼다.

**`03_count.sql` 3번 쿼리가 로그와 어긋났다.** 로그에는 100건 다 `발송실패` 인데
알림함 집계는 성공 100 · 실패 0 으로 나왔고, 드레인 시간은 `NULL` 이었다. 성공
100 이면 `sent_at` 이 차 있어야 하므로 앞뒤가 안 맞는다. 다음 측정에서 다시 확인해야
한다.
