## 한계 찾기 — 건수를 올려가며

알림 건수를 늘려가며 **한 번의 실행이 1분을 넘기는 지점**을 찾는다. 스케줄러는
단일 스레드로 하나씩 보내므로, 1분을 넘기면 다음 실행이 제때 못 뜨고 밀린다.

`01_setup.sql` 의 `@COUNT` 만 바꿔가며 같은 순서로 돌린다.

| 건수 | 처리 시간 | 1건 중앙값 | p95 | RPS | QPS | TPS | 건당 쿼리 | 건당 읽은행 |
|---|---|---|---|---|---|---|---|---|
| 100 | 46.2 초 | 346 ms | 895 ms | 2.2 | 35 | 35 | 16.4 | 96.0 |
| **200** | **69.1 초** | 299 ms | 765 ms | **2.9** | **67** | **55** | 23.2 | 118.9 |
| **300** | **103.3 초** | 294 ms | 875 ms | **2.9** | **68** | **55** | 23.3 | 169.8 |
| **500** | **182.5 초** | 320 ms | 841 ms | **2.7** | **63** | **52** | 23.2 | 288.5 |

> `QPS`·`TPS` 는 스냅샷 차이를 **실제 발송 시간**으로 나눈 값이다. 스크립트가
> 보여주는 값은 스냅샷 사이(124.8 · 188.0 · 226.9초)로 나눈 것이라 창 길이에 따라
> 달라진다. 창에는 알림 시각을 기다린 시간이 절반 넘게 들어 있다.

## 한계는 165 ~ 175건

세 라운드가 거의 같은 값을 준다.

```
200건 ÷ 69.1초  = 2.89 건/초   × 60 = 174건
300건 ÷ 103.3초 = 2.90 건/초   × 60 = 174건
500건 ÷ 182.5초 = 2.74 건/초   × 60 = 164건
```

```
165 ~ 175건까지    한 실행이 1분 안에 끝난다
그보다 많으면       다음 실행이 제때 못 뜨고 밀린다
```

500건에서 6% 떨어졌다. 오차일 수도 있으나 **커질수록 아주 조금씩 나빠지는
방향**이다.

### 처리량은 안 꺾였다

건수를 3배로 늘려도 **초당 처리량이 2.9 로 그대로다.** 단일 스레드로 하나씩
보내므로 자원이 포화되는 지점이 아직 안 나왔다.

그래서 여기서 말하는 한계는 **"처리량이 꺾이는 곳" 이 아니라 "한 실행이 1분을
넘기는 건수"** 다.

### 100건 라운드는 이상치였다

```
        RPS    중앙값     p95      QPS   TPS   건당 쿼리
100건   2.2    346 ms   895 ms    35    35    16.4
200건   2.9    299 ms   765 ms    67    55    23.2
300건   2.9    294 ms   875 ms    68    55    23.3
500건   2.7    320 ms   841 ms    63    52    23.2
```

**200·300·500 이 서로 맞고 100 만 떨어져 있다.** 그때 느린 건이 많이 섞였고(p95 895),
100건을 세 번 돌렸을 때 34~46초로 흔들린 것과 같은 이야기다.

**한 번 재고 결론 내리면 안 된다**는 것이 이 표의 또 다른 소득이다.

### 읽은 행이 건수의 제곱으로 늘어난다

```
건수    건당 읽은행    전체 읽은 행    ÷ 건수²
100       96.0         9,600       0.96
200      118.9        23,780       0.59
300      169.8        50,940       0.57
500      288.5       144,250       0.58
```

**200 부터 0.58 로 딱 맞는다.** 우연이 아니라 `N²` 에 비례한다.

`N²/2` 는 **"실행 중에 1행씩 커지는 테이블을 매 건마다 훑는"** 모양이다.
1 + 2 + ... + N 이기 때문이다.

건당 쿼리는 23 으로 고정인데 **읽은 행만 는다.** 쓰기 쪽은 정확하다.

```
넣은 행    501    알림함 500 + 스냅샷 1
고친 행   1001    예약 500 + 알림함 500
```

원인은 아직 못 찾았다. `UserNotificationService.create` 는 조회 없이 `save` 만
하고, `performance_schema` 의 문장별 통계는 이 서버에서 조회가 막혀 있었다.
**인덱스를 넣고 다시 재면 갈릴 것이다.**

인덱스로 콕 집어 읽는다면 **건당 읽은 행은 건수와 무관하게 일정해야** 한다. 늘어난다는
것은 알림 하나를 처리할 때마다 **데이터가 많아진 만큼 더 읽고 있다**는 뜻이고,
어딘가에 스캔이 있다는 신호다.

### 스케줄러 조회가 전체 스캔이었다

`EXPLAIN` 으로 확인한 결과다.

```
fcm_token        type=ref    FK 인덱스     rows=1     정상
users_settings   type=const  유니크 키     rows=1     정상
schedules_alarm  type=ALL    key 없음                 전체 스캔
```

`SHOW INDEX FROM schedules_alarm` 을 보면 인덱스가 둘뿐이다.

```
PRIMARY                       schedules_alarm_id
UKml5ta1grdso2f1n7dfq4nr2j0   schedules_id
```

**`alarm_date_time` 에도 `is_sent` 에도 인덱스가 없다.** 스케줄러가 1분마다
`schedules_alarm` 을 통째로 읽는다. 지금은 예약이 적어 티가 안 나지만, 지난 알림도
계속 남으므로 서비스가 오래될수록 스캔이 커진다.

```sql
CREATE INDEX idx_alarm_pending ON schedules_alarm (status, alarm_date_time);
```

등호 조건(`status`)이 앞, 범위 조건(`alarm_date_time`)이 뒤여야 인덱스를 끝까지
탄다.

### 100건을 세 번 돌려보니

| 회차 | 처리 시간 | 중앙값 | p95 |
|---|---|---|---|
| 1회 | 34.2 초 | 318 ms | 464 ms |
| 2회 | 37.6 초 | 330 ms | 600 ms |
| 3회 | **46.2 초** | 346 ms | **895 ms** |

**중앙값은 ±4% 로 안정적인데 p95 는 두 배 차이가 난다.** 느린 건이 몇 개 섞이면
전체 시간이 그만큼 늘어나, 처리 시간도 34~46초로 흔들린다.

그래서 **개선 전후를 비교할 때 처리 시간 하나로 판단하면 안 된다.** 중앙값을
같이 봐야 한다.

### 아직 모르는 것

```
읽은 행이 왜 느는지   전체 스캔은 실행당 1회라 건당으로는 상수여야 한다.
                   이것만으로는 설명이 안 된다
더 큰 규모          500 · 1000 에서도 RPS 2.9 가 유지되는지
```

**인덱스를 넣고 다시 재면 갈린다.** 인덱스 때문이면 확 줄고, 아니면 그대로일 것이다.

**절차**

```
1  docker compose stop app

3  2분 대기
4  docker compose start app
5  로그와 DB 를 5분간 관찰
```

**개선 전** — 2026-08-25 측정

알림 시각을 `17:03:41` 로 맞춘 뒤 서버를 껐고, 그 분이 지난 다음 다시 켰다.

| 항목 | 값 |
|---|---|
| 도달 | **0 / 100** |
| `is_sent = false` 로 남은 건수 | **100** |
| 울릴 시각이 지났는데 미발송 | **100** |
| 알림함에 만들어진 줄 | **0** |
| 이후 실행에서 재조회된 건수 | **0** |

로그는 재시작 이후 계속 `count=0` 이었다.

```
[ALARM] 조회 window=2026-08-25T17:05~17:06 count=0
[ALARM] 조회 window=2026-08-25T17:06~17:07 count=0
```

**알림함 줄이 0건이라는 게 핵심이다.** 알림함은 발송을 시도하기 전에 만들어지므로,
0건이라는 것은 **스케줄러가 그 알림을 집지도 않았다**는 뜻이다. 보내려다 실패한
것이 아니라 시도 자체가 없었다.

> `SUM()` 결과가 `NULL` 로 나오는 것은 셀 행이 0개이기 때문이다. 오류가 아니다.

## 실험 C — 정상 발송 100건

유실이 아니라 **정상으로 나갈 때 얼마나 걸리는지**를 본다. 재시도 간격을 정하려면
한 번 도는 데 걸리는 시간을 알아야 한다.

**절차**

```
1  토큰이 살아 있는지 확인한다
2  02_reset.sql   @AFTER_MIN = 2
3  05_metrics.sql 실험 전 스냅샷
4  2분 대기 — 100건이 나간다
5  05_metrics.sql 실험 후 스냅샷
6  docker compose logs app --since 15m > app.log
   python3 06_latency.py app.log
```

**결과** — 2026-08-28 측정 · 100건 전부 성공

| 항목 | 값 | 무엇인가 |
|---|---|---|
| 100건 소요 | **34.2 초** | 첫 발송시도 ~ 마지막 완료표시 |
| 1건 중앙값 | **318 ms** | 발송시도 ~ 완료표시 |
| 1건 평균 | 342 ms | |
| p95 | 464 ms | 느린 쪽 5% 의 경계 |
| 최소 · 최대 | 253 ~ 584 ms | |
| RPS | 2.9 | 초당 처리한 알림 수 |
| QPS | 68 | 초당 DB 쿼리 수 |
| TPS | 56 | 초당 DB 커밋 수 |

**한 번 더 쟀을 때도 37.6초 · 중앙값 330ms 로 10% 안에서 맞았다.** 한 번만 재면
그날 상태였을 수 있어 두 번 돌렸다.

> QPS·TPS 는 스냅샷 두 개의 차이(쿼리 2,328 · 커밋 1,907)를 **실제 발송 시간
> 34.2초**로 나눈 값이다. 스냅샷 사이는 91.4초였지만 그중 절반 넘게가 알림 시각을
> 기다린 시간이라, 그걸로 나누면 부하가 희석된다.

### 구간을 쪼개면

`건너뜀` 로그는 토큰 목록이 비어 반환하는 자리에 찍히는데, **그 지점이 곧 FCM 호출
직전**이다. 토큰을 지운 실행을 그 구간의 값으로 쓸 수 있다.

```
발송시도
  │  알림함 INSERT · 설정 조회 · 토큰 조회      29 ms      토큰 없는 실행
  ├─ FCM 직전
  │  FCM 왕복                                289 ms     318 − 29
  ├─ 전송성공
  │  알림함 발송표시 · 예약 완료표시             21 ms      339 − 318
  └─ 완료표시                                339 ms
```

```
FCM 왕복    289 / 339 = 85%
DB 합계      50 / 339 = 15%
```

**시간의 85% 가 FCM 왕복이다.** 배치 발송(`sendEach`)이 처리량 개선의 유일한 큰
수라는 근거가 여기서 나온다. 지연 로딩을 고쳐도 나머지 15% 안에서 움직인다.

토큰을 지운 실행은 FCM 을 아예 안 타므로 **「FCM 제외」 상한선**이기도 하다.

```
FCM 포함    초당 2.9 건    분당 175 건
FCM 제외    초당 25 건     분당 약 1,500 건      100건 3.99초
```

**FCM 왕복이 처리량을 9배 떨어뜨린다.**

### DB — 알림 1건당

| 항목 | 값 | 예상 |
|---|---|---|
| 쿼리 | **23.3** | 3~5 |
| 커밋 | **19.1** | 1~3 |
| 읽은 행 | **66.8** | 십 몇 |
| 넣은 행 | 1.0 | 1 (알림함) |
| 고친 행 | 2.0 | 2 (예약 · 알림함) |

**넣은 행과 고친 행은 예상과 정확히 맞는다.** 실제로 데이터를 바꾸는 건 `INSERT`
1회 · `UPDATE` 2회뿐이다.

그런데 **쿼리가 23개, 커밋이 19번**이다. 스케줄러에 `@Transactional` 이 없어
리포지토리 호출마다 자기 트랜잭션을 열기 때문이다.

```
알림함 저장       BEGIN · INSERT · COMMIT
설정 조회        BEGIN · SELECT · COMMIT
토큰 조회        BEGIN · SELECT · COMMIT
알림함 발송표시    BEGIN · UPDATE · COMMIT
예약 완료표시      BEGIN · UPDATE · COMMIT
```

이건 **의도한 대가**다. 하나의 트랜잭션으로 묶으면 100건을 돌다 50건째에 죽었을
때 앞의 49건이 통째로 롤백된다. 지금은 병목이 아니므로(FCM 이 85%) 그대로 둔다.

**읽은 행 66.8 은 아직 원인을 모른다.** 인덱스 조회만 하면 십 몇 행이면 될 자리다.
`fcm_token` · `users_settings` 조회가 인덱스를 못 타는지 `EXPLAIN` 으로 확인해야 한다.

### 실패했을 때 `(n=1, 다시 측정 필요)`

| 상황 | 시각 | 소요 |
|---|---|---|
| 실패 (SENDER_ID_MISMATCH) | `23:50:00.073` → `23:50:01.578` | 1,505 ms |
| 실패 (THIRD_PARTY_AUTH_ERROR) | `01:30:00.041` → `01:30:03.028` | 2,987 ms |

**둘 다 한 건씩만 잰 값이다.** 토큰을 지운 실행은 `건너뜀`(FCM 미호출)이고 위
실험은 전부 성공이라 **진짜 실패 케이스가 비어 있다.** `UNAVAILABLE` 같은 응답을
만들려면 가짜 FCM 이 필요하다.

## 관찰 기록

측정하면서 예상과 달랐던 것, 다시 재야 했던 것.

**896ms 는 과대평가였다.** 처음에는 로그에서 눈에 띈 한 줄을 집어 `n=1` 로 썼는데,
100건을 다 뽑으니 중앙값이 318~330ms 였다. 최대가 1,399ms 인 것을 보면 **꼬리 쪽
값을 대푯값으로 삼았던 셈**이다. 그 값에서 나온 "분당 66건" 도 실제로는 159~175건
이었다.

**토큰을 지우면 FCM 을 아예 안 탄다.** 실패를 만들려고 토큰을 지웠는데
`sendToUser` 가 토큰 목록이 비면 FCM 호출 전에 반환한다. 로그에 `건너뜀
사유=토큰없음` 만 찍히고 `전송실패` 는 없다. 실패 케이스를 만들려면 가짜 FCM 이
필요하다. 대신 이 실행이 **뜻하지 않게 「FCM 제외」 측정**이 되었다.

**`Com_*` 는 `performance_schema.global_status` 에 없었다.** `SHOW GLOBAL STATUS
LIKE 'Com_commit'` 으로는 나오는데 테이블에는 `Com_stmt_reprepare` 하나뿐이었다.
`Handler_commit` · `Innodb_rows_*` 로 바꿔서 같은 것을 봤다.

**`03_count.sql` 3번 쿼리가 로그와 어긋났다.** 로그에는 100건 다 `발송실패` 인데
알림함 집계는 성공 100 · 실패 0 으로 나왔고, 드레인 시간은 `NULL` 이었다. 성공
100 이면 `sent_at` 이 차 있어야 하므로 앞뒤가 안 맞는다. 다음 측정에서 다시 확인해야
한다.
