# 밀린 알림이 쌓일 때의 처리량

> **상태** 대기 중 — [재처리 글](../retry/)이 끝난 뒤 시작
> 앞선 글: [알림 스케줄러 개요](../README.md)

---

## 1. 재처리를 넣으면 밀린 게 쌓인다

앞 글에서 조회를 상태 기준으로 바꿨다.

```sql
WHERE is_sent = false AND alarm_date_time <= :now
```

유실은 사라졌지만 **버리지 않으니 쌓인다.**

```
전    밀리면 그 분을 버린다      →  유실.  대신 쌓이지 않는다
후    밀리면 다음이 집어간다     →  유실 없음.  대신 쌓인다
```

장애가 10분 이어졌다면 10분치가 다음 한 번의 실행에 몰린다.
**그걸 얼마나 빨리 비울 수 있는지가 이 글의 주제다.**

---

## 2. 지금 얼마나 걸리는가

발송은 알림 하나씩 순서대로 한다.

```java
for (SchedulesAlarm alarm : alarms) {
    fcmNotificationService.sendToUser(user, ...);   // 네트워크 호출. 끝날 때까지 기다린다
}
```

그리고 `sendToUser` 안에서도 **토큰 하나에 왕복 한 번**이다.

```java
for (FcmToken fcmToken : tokens) {
    FirebaseMessaging.getInstance().send(message);   // 1건 = 1왕복
}
```

실측값은 추적 로그에 이미 남아 있다.

| 상황 | 시각 | 소요 |
|---|---|---|
| 성공 | `02:55:00.022 발송시도` → `02:55:00.918 전송성공` | **896 ms** |
| 실패 (SENDER_ID_MISMATCH) | `23:50:00.073` → `23:50:01.578` | **1,505 ms** |
| 실패 (Invalid APNs credential) | `01:30:00.041` → `01:30:03.028` | **2,987 ms** |

**실패가 성공보다 2~3배 느리다.**

---

## 3. 언제부터 겹치는가

`@Scheduled` 는 기본이 단일 스레드다. 이번 실행이 안 끝나면 다음 실행이 뜨지
못한다.

```
성공만 0.9초    →   약 66건이면 1분을 채운다
실패가 3초      →   약 20건이면 1분을 채운다
```

**나빠질 때 더 빨리 나빠진다.** FCM 장애나 토큰 대량 만료로 실패가 몰리면,
실패가 느려서 더 밀리고, 밀려서 더 쌓인다.

---

## 4. 겹치면 무슨 일이 나는가

흔한 오해부터 정리한다. **"분당 66건" 은 처리 한도가 아니다.**

```
14:31:00   실행 시작 → 100건을 한 번에 조회 → 하나씩 발송
14:32:00   다음 틱이지만 앞이 안 끝나 못 뜸        ← 이 틱을 건너뜀
14:32:30   90초 걸려 100건 다 보냄
14:33:00   다음 실행 → 남은 게 없음
```

**100건 전부 나간다.** 40건이 잘리는 게 아니라 한 번의 실행이 90초 도는 것이다.

문제는 **그 90초 동안 새로 시각이 된 알림을 못 잡는다**는 것.

```
14:32:00 에 울릴 알림   →  14:33 실행에서야 잡힘   →  1분 늦음
```

밀린 게 많을수록 새 알림도 같이 늦어진다. **지연이 눈덩이처럼 커진다.**

다만 **유실로는 이어지지 않는다.** 상태 기반 조회라 늦어도 결국 간다.
재처리 구조가 겹침의 피해를 흡수한 결과다. 그래서 이 문제는 "유실"이 아니라
"지연"이고, 우선순위가 낮다.

## 5. 개선 방법

### 5-1. 왕복 횟수를 줄인다 — 효과가 가장 크다

Firebase Admin SDK 에는 여러 건을 한 번에 보내는 API 가 있다.

```java
FirebaseMessaging.getInstance().sendEach(messages);   // 최대 500건 = 1왕복
```

```
100건    지금  100왕복 × 0.9초 = 90초
        배치   1왕복        ≈ 1초
```

**코드 변경이 작은데 효과가 가장 크다.** 결과도 건별로 돌아와 어떤 게
실패했는지 그대로 알 수 있다.

다만 구조를 바꿔야 한다. 지금은 **알림 하나마다 발송하고 바로 상태를 저장**
하는데, 배치로 보내려면 **모아서 한 번에 보내고 결과를 흩어 반영**해야 한다.

### 5-2. 병렬로 보낸다

스레드 풀을 두고 동시에 여러 건을 보낸다. 간단해 보이지만 딸려오는 게 많다.

```
지연 로딩     alarm.getSchedules() 가 다른 스레드에서 안 됨. 미리 로딩 필요
트랜잭션      스레드마다 커넥션을 잡음. 풀 크기와 맞물림
FCM 할당량    동시에 너무 많이 던지면 서버 쪽에서 막힘
거부 정책     큐가 차면 어떻게 할지 정해야 함
```

**5-1 로 부족할 때 쓰는 카드다.** 배치가 왕복 자체를 줄이므로 병렬화보다 먼저다.

### 5-3. 조회를 고친다 (2-6)

```java
Schedules schedule = alarm.getSchedules();   // 알람마다 추가 쿼리
Users user = schedule.getUsers();            // 또 추가 쿼리
```

`findTargetAlarms` 에 `JOIN FETCH` 가 없어 **알람 수만큼 쿼리가 늘어난다.**
같은 리포지토리의 `findSentAlarmsByUsersId` 에는 이미 있으므로 맞추면 된다.

그리고 메서드에 `@Transactional` 이 없어 지연 로딩 시점의 영속성 컨텍스트
보장이 불확실하다. 다만 **외부 API 호출을 트랜잭션 안에 두면 커넥션을
점유하므로**, 트랜잭션 경계를 어디에 둘지는 배치 구조와 함께 정해야 한다.

### 5-4. 스케줄러가 겹치는 걸 허용한다 — 권하지 않음

스레드 풀 스케줄러로 바꾸면 앞이 안 끝나도 다음이 뜬다. 밀리지 않는다.

**그런데 두 실행이 같은 알림을 집는다.**

```
실행 A   알림 5번을 집어 발송 중
실행 B   아직 is_sent = false 라 5번을 또 집음   →  중복 발송
```

상태 전이(`PENDING → SENDING → SENT`)나 락이 먼저 있어야 안전하다.
지금 구조에서 이것부터 하면 안 된다.

## 7. 이 작업을 할 것인가

**아직 정하지 않았다.**

```
지금 발송량        하루 몇 건
겹치기 시작하는 선  분당 20~66건
```

한참 멀다. 그리고 재처리 구조 덕분에 겹쳐도 유실은 나지 않는다.

재처리를 끝내고 **밀린 게 쌓이는 걸 실제로 본 뒤**, 지연이 정말 걸리는지 보고
정한다. 지금 미리 정해두면 결과를 거기에 맞추게 된다.

안 하기로 하면 재처리 글의 마지막에 한 문단으로 남긴다.

```
발송이 1건당 0.9초(성공)·최대 3초(실패)라 분당 20~66건에서 스케줄이 겹치기 시작한다.
다만 겹쳐서 실행이 밀리는 것도 결국 "그 분을 건너뛰는" 것과 같아,
재처리 구조를 갖추면 유실로는 이어지지 않는다.
배치 발송과 병렬화는 현재 발송량이 그 선에 못 미쳐 뒤로 두었다.
```

**"안 고쳤다" 가 아니라 "재보고 뒤로 미뤘다" 가 된다.**
