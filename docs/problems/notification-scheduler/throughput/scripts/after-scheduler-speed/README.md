# 동시성 N 을 얼마로 둘지 정하는 테스트

> 본문: [알림 처리량 개선기](../../README.md)

스레드를 몇 개 두면 분당 몇 건이 되는지, 어디서 더 안 오르는지 잰다.

---

## 왜 세 사람에게 나눠 보내나

FCM 은 **한 기기에 분당 240건**까지만 받는다. 한 사람에게 몰면 N=2 부터 우리 코드가
아니라 FCM 의 스로틀링을 재게 된다.

| 대상 | 기기 | OS |
|---|---|---|
| `users_id = 32` | IOS | 18.6 |
| `users_id = 33` | IOS | 26.6.1 |
| `users_id = 265` | ANDROID | 16 |

세 대면 분당 720건까지 안전하다.

| N | 예상 분당 | 기기당 | 실제 FCM 으로 잴 수 있나 |
|---|---|---|---|
| 1 | 150 ~ 180 | 60 | O |
| 2 | 300 ~ 360 | 120 | O |
| 4 | 600 ~ 720 | 240 | O (경계) |
| 8 이상 | 1,200+ | 400+ | X — 기기 제한에 걸린다 |

**N=8 위쪽은 이 방법으로 못 잰다.** 그 구간은 FCM 을 스텁으로 바꾸고 따로 봐야 한다.

---

## 하기 전에

- **세 사람 다 기기 알림을 꺼둔다.** 한 라운드에 1,000건이 나간다.
- 그라파나에 이 넷을 띄워둔다.
  - `system_cpu_usage{application="toit-test"} * 100`
  - `hikaricp_connections_active{application="toit-test"}`
  - `hikaricp_connections_pending{application="toit-test"}`
  - `hikaricp_connections_timeout_total{application="toit-test"}`

`pending` 이 0 을 벗어나면 스레드가 커넥션을 기다리는 것이다. **그 지점이 N 의 상한**
이다. 더 올려도 처리량이 안 오르고 API 응답만 느려진다.

---

## 한 라운드

```
1  application.properties 의 alarm.send.concurrency 를 N 으로 바꾸고 재시작
2  01_setup.sql            1,000건을 세 사람에게 나눠 심는다
3  기다린다                 N=1 이면 6분쯤, N=4 면 2분쯤
4  02_count.sql            대기중이 0 이 될 때까지 1분 간격으로 돌린다
5  로그를 받아 04_latency.py
6  그라파나 네 패널 캡처
7  03_teardown.sql
8  N 을 바꿔 1번부터
```

로그는 이렇게 받는다.

```bash
docker compose logs app --since 15m > run-n1.log
python3 04_latency.py run-n1.log
```

## 무엇을 보나

`04_latency.py` 출력에서 셋을 본다.

```
[1] 23:05:00   조회 1000건   스레드 4개
    1건 전체   중앙값 290 ms · p95 410 ms
    처리       92.0 초  ·  분당 652 건
    실효 동시성 3.2  (스레드 4개)
```

- **분당** — N 을 두 배로 올렸을 때 이 값이 따라 오르면 성공이다.
- **1건 전체 중앙값** — N 을 올려도 안 변해야 한다. 늘어나기 시작하면 어딘가
  막힌 것이다 (커넥션 풀이 유력).
- **실효 동시성** — `분당 ÷ 60 × 1건 시간`. 리틀의 법칙으로 되짚은 값이다.
  스레드 개수보다 눈에 띄게 작으면 스레드가 놀고 있다는 뜻이다.

`02_count.sql` 에서는 **대기중** 과 **기기별 실패** 를 본다.

- 대기중이 남으면 10분 창을 넘겨 잘린 것이다 → 그 N 은 1,000건을 감당 못 한 것
- 한 사람 몫만 실패가 몰리면 그 기기가 240건 제한에 걸린 것이다 → 그 라운드는 버린다
