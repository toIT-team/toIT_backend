> 본문: [알림 처리량 개선기](README.md) · 앞 글 자료: [retry/measurements.md](../retry/measurements.md)

측정 환경과 원자료를 남긴다. 본문에는 결론만 싣고, 재현에 필요한 것은 여기에 둔다.

## 측정 환경

```
서버        2 vCPU / 2 GB, 단일 인스턴스   (application="toit-test")
DB          MySQL 8.0
스케줄러     @Scheduled(cron = "0 * * * * *")   매분 0초, 단일 스레드
코드 기준    재처리 구조 적용 후 (status · attempt_count · next_attempt_at)
```

**앞 글의 "개선 후" 가 이 글의 "개선 전" 이다.** `is_sent` 시절 값과 섞지 않는다.
로그 형식으로 구분한다.

```
window=...        is_sent 시절
now=... oldest=   재처리 적용 후    ← 이 글이 쓰는 값
```

## 4. 만료는 정말 조용한가 — 2026-08-30

`scripts/01_expired_setup.sql` · `02_check.sql`

밀리는 상황을 만들지 않고, **처음부터 시한을 넘긴 채로** 200건을 만들었다.

```
세팅 시각        11:24:16
alarm_date_time  11:13:16     (11분 전)
status           PENDING
```

### 대조 — 시한 조건 하나만 뺐다 넣었다

```
시한 조건을 빼면    200건
시한 조건을 넣으면    0건
```

같은 데이터에 조건 하나만 갈아끼운 것이라, **다른 조건 때문에 빠진 것이 아님**이
확인된다.

### 로그 — 14번 연속 `count=0`

```
11:25   조회 now=11:25 oldest=11:15 count=0
11:26   조회 now=11:26 oldest=11:16 count=0
11:31   조회 now=11:31 oldest=11:21 count=0
11:32   조회 now=11:32 oldest=11:22 count=0
11:33   조회 now=11:33 oldest=11:23 count=0
11:34   조회 now=11:34 oldest=11:24 count=0
11:35   조회 now=11:35 oldest=11:25 count=0
11:36   조회 now=11:36 oldest=11:26 count=0
11:37   조회 now=11:37 oldest=11:27 count=0
11:38   조회 now=11:38 oldest=11:28 count=0
```

`oldest` 가 매분 1분씩 앞으로 간다. 알림 시각 `11:13` 에서 **멀어지기만 한다.**

> `11:22` · `11:23` · `11:24` 의 `count=0` 은 데이터가 생기기 전이라 근거가 아니다.
> 세팅이 `11:24:16` 이므로 `11:25` 부터가 유효하다.

### 상태 — 시간이 지나도 그대로

| | 13분 뒤 (11:26) | 23분 뒤 (11:36) |
|---|---|---|
| 전체 | 200 | 200 |
| 대기중 (`PENDING`) | 200 | 200 |
| 발송됨 (`SENT`) | 0 | 0 |
| 포기 (`FAILED`) | 0 | 0 |
| 시도한 적 있음 (`attempt_count > 0`) | 0 | 0 |
| 오류코드 남음 | 0 | 0 |
| 재시도 예약됨 | 0 | 0 |
| 알림함 줄 | 0 | 0 |

**23분이 지나도 아무것도 안 바뀐다.** `FAILED` 로 가지도, 알림함에 줄이 생기지도,
로그에 `발송시도` 가 한 줄 남지도 않는다.

## 5. 밀려서 유실에 이르는가 — 2026-08-30

`scripts/06_backlog_setup.sql` · `07_backlog_count.sql`

4번은 **이미 만료된 뒤**를 봤다. 여기서는 **밀려서 만료에 이르는 과정**을 재현한다.

### 왜 500건으로는 안 되나

조회에 `LIMIT` 가 없어서 한 번에 다 집어간다. 500건이 199초 걸려도 그 실행 안에서
전부 나간다. **유실은 "집히기 전에 방치된 것" 에만 생긴다.**

그래서 두 덩이로 나눴다.

```
홀딩   2,500건을 지금 시각으로     스케줄러를 오래 붙잡는다
유입     200건을 1~20분 뒤로 10건씩  붙잡힌 동안 도착해 방치된다
```

발송은 진짜 FCM 으로 했다. **기기의 앱 알림만 꺼두면** 왕복은 그대로고 화면만
조용하다. `users_settings` 를 끄면 조회에서 걸러져 발송 자체가 안 되므로 그쪽이
아니다.

### 실행 기록

```
14:31:00   조회 count=2500   →  770.7초(12.8분) 처리
14:44:00   조회 count=100    oldest=14:34
14:45 ~ 14:51   count=10 씩
```

### 결과

| 구분 | 전체 | 발송됨 | 대기중 |
|---|---|---|---|
| 홀딩 | 2,500 | 2,500 | 0 |
| 유입 | 200 | 170 | **30** |

유입을 분별로 보면 경계가 정확히 갈린다.

| 몇 분 뒤 | 울릴 시각 | 결과 |
|---|---|---|
| 01분 | 14:31:59 | 대기중 |
| 02분 | 14:32:59 | 대기중 |
| 03분 | 14:33:59 | 대기중 |
| **04분** | **14:34:59** | **발송됨** |
| 05 ~ 20분 | ~ 14:50:59 | 발송됨 |

`14:44` 틱의 `oldest` 가 `14:34` 다. **`14:33:59` 는 그보다 앞이라 창 밖, `14:34:59`
는 안쪽이다.** 30건이 갈린 자리가 여기다.

산수와도 맞는다.

```
12.8분 밀림 − 10분 창 = 2.8분치가 창 밖
2.8분 × 분당 10건 = 28건  ≈  30건
```

### 유실된 30건에 아무 기록이 없다

```
status              PENDING
attempt_count       0
last_error_code     NULL
알림함 줄            없음
```

**시도조차 안 했다.** 4번에서 본 것과 같은데, 이번에는 **실제로 밀려서** 그렇게 됐다.

### 처리율이 지난번보다 빨랐다

```
이번    2,500건 / 770.7초  =  3.24 건/초  =  분당 195건    1건 중앙값 284 ms
지난번  100 ~ 500건        =  2.5 ~ 2.9   =  분당 150~175   1건 중앙값 330 ms
```

**건수를 다섯 배로 늘렸는데 오히려 빨랐다.** 그러면 1번의 "500건만 어긋난다" 도
배치 크기 탓이 아니라 **FCM 왕복 시간이 날마다 다른 것**으로 읽힌다.

한계는 **분당 150 ~ 195건**으로 넓혀 잡는 게 맞다.

### 곁가지 — 한 건의 예외가 실행 전체를 끝낸다

세팅을 두 번 돌린 탓에 이런 예외가 났다.

```
14:30:59  ObjectOptimisticLockingFailureException:
          Row was updated or deleted by another transaction [UserNotification#3103]
```

첫 실행이 처리 중일 때 두 번째 실행의 정리 구문이 그 행을 지웠다. **그 실행은
거기서 끝났다.** 173건만 나가고 나머지는 그대로 남았다.

`checkAndSendAlerts` 의 루프에 `try/catch` 가 없다. **한 건이 터지면 그 실행의
나머지가 통째로 버려진다.** 상태 기반이라 다음 틱에 회수되지만, 밀린 상황에서는
그만큼 더 밀린다.

> `06_latency.py` 의 `[1] 14:30:00` 항목은 이 죽은 실행이다. 실험은 `[2]` 다.

## 6. 타임아웃 계산

관측이 아니라 **설정값으로 계산한 것**이다.

```java
// FcmConfig
.setConnectTimeout(3_000)
.setReadTimeout(5_000)
```

```
한 건 평균 = (1 − 타임아웃 비율) × 0.4초  +  타임아웃 비율 × 5초
10분 ÷ 한 건 평균 = 10분 안에 비울 수 있는 양
```

| 타임아웃 비율 | 한 건 평균 | 10분 안에 비울 양 |
|---|---|---|
| 0 % | 0.40 초 | 1,500건 |
| 1 % | 0.45 초 | 1,340건 |
| 5 % | 0.63 초 | 950건 |
| 10 % | 0.86 초 | 700건 |
| 50 % | 2.70 초 | 220건 |
| 100 % | 5.00 초 | 120건 |

`0.4초` 는 네 라운드 중 **가장 느렸던 500건**(RPS 2.51)에서 역산했다. 빠른 쪽
(0.345초)으로 계산하면 `1,740 → 740` 이 되는데, **어느 쪽을 써도 절반 이하**라
불리한 값을 썼다.

실패 한 건의 실제 소요는 재보지 못했다. 만들 수 있는 실패(가짜 토큰)는 FCM 이 형식만
보고 거절하는 **빠른 실패**라 재고 싶은 것과 다르고, 느린 실패(APNs 경유)는 Firebase
설정을 일부러 깨야 나온다.

## 관찰 기록

### 처리율이 날마다 흔들린다

```
2026-08-29   1건 330 ms   분당 150 ~ 175건
2026-08-30   1건 284 ms   분당 195건        (2,500건 라운드)
```

같은 코드, 같은 서버인데 **하루 사이에 30% 가까이 벌어졌다.** 한 건의 85% 가 FCM
왕복이므로 그쪽이 흔들리면 전체가 흔들린다. **한계를 하나의 숫자로 못 박으면
안 된다.**

### 500건만 계산과 어긋난다

`1 ÷ 중앙값` 으로 본 상한과 실측을 견주면 셋은 맞고 하나가 벌어진다.

| 건수 | 1건 중앙값 | 1 ÷ 중앙값 | 실측 RPS |
|---|---|---|---|
| 100 | 332 ms | 3.0 | 2.8 |
| 200 | 341 ms | 2.9 | 2.8 |
| 300 | 330 ms | 3.0 | 2.9 |
| 500 | 295 ms | **3.4** | **2.5** |

한 건 자체는 오히려 빨랐는데(295 ms) 전체는 느렸다. 건 사이의 틈도 아니었다(11~13 ms).
남는 설명은 **꼬리**다. `p95` 가 300건 400 ms 에 견줘 500건은 869 ms 로 두 배다.
중앙값은 꼬리를 못 본다.

원인은 더 갈라보지 않았다. FCM 이 외부라 3분 넘게 도는 동안 응답이 출렁일 여지가
있고, 이 글의 결론(하나씩 보내서 느리다)은 앞의 세 라운드로 충분하다.

### 조회에 상한이 없다

```java
List<SchedulesAlarm> alarms = schedulesAlarmRepository.findTargetAlarms(now, oldest);
```

`LIMIT` 도 `Pageable` 도 없다. 밀린 것을 전부 한 번에 메모리로 올린다. 500건까지는
재봤지만 **1,500건을 한 번에 들 수 있는지는 안 재봤다.** 힙은 이번 측정에서 보지
않았다.
