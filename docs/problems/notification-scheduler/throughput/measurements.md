## 측정 환경

```
서버        2 vCPU / 2 GB, 단일 인스턴스   (application="toit-test")
DB          MySQL 8.0
스케줄러     @Scheduled(cron = "0 * * * * *")   매분 0초, 단일 스레드
```

**앞 글의 "개선 후" 가 이 글의 "개선 전" 이다.** `is_sent` 시절 값과 섞지 않는다.

```
window=...        is_sent 시절
now=... oldest=   재처리 적용 후    ← 이 글이 쓰는 값
```

## 4. 만료는 정말 조용한가 — 2026-08-30

`scripts/01_expired_setup.sql` · `02_check.sql`

밀리는 상황을 만들지 않고, **처음부터 시한을 넘긴 채로** 200건을 만들었다.

```
세팅 시각        11:24:16
alarm_date_time  11:13:16     (11분 전)
status           PENDING
```

### 대조 — 시한 조건 하나만 뺐다 넣었다

```
시한 조건을 빼면    200건
시한 조건을 넣으면    0건
```

같은 데이터에 조건 하나만 갈아끼운 것이라, **다른 조건 때문에 빠진 것이 아님**이
확인된다.

### 로그 — 14번 연속 `count=0`

```
11:25   조회 now=11:25 oldest=11:15 count=0
11:26   조회 now=11:26 oldest=11:16 count=0
11:31   조회 now=11:31 oldest=11:21 count=0
11:32   조회 now=11:32 oldest=11:22 count=0
11:33   조회 now=11:33 oldest=11:23 count=0
11:34   조회 now=11:34 oldest=11:24 count=0
11:35   조회 now=11:35 oldest=11:25 count=0
11:36   조회 now=11:36 oldest=11:26 count=0
11:37   조회 now=11:37 oldest=11:27 count=0
11:38   조회 now=11:38 oldest=11:28 count=0
```

`oldest` 가 매분 1분씩 앞으로 간다. 알림 시각 `11:13` 에서 **멀어지기만 한다.**

> `11:22` · `11:23` · `11:24` 의 `count=0` 은 데이터가 생기기 전이라 근거가 아니다.
> 세팅이 `11:24:16` 이므로 `11:25` 부터가 유효하다.

### 상태 — 시간이 지나도 그대로

| | 13분 뒤 (11:26) | 23분 뒤 (11:36) |
|---|---|---|
| 전체 | 200 | 200 |
| 대기중 (`PENDING`) | 200 | 200 |
| 발송됨 (`SENT`) | 0 | 0 |
| 포기 (`FAILED`) | 0 | 0 |
| 시도한 적 있음 (`attempt_count > 0`) | 0 | 0 |
| 오류코드 남음 | 0 | 0 |
| 재시도 예약됨 | 0 | 0 |
| 알림함 줄 | 0 | 0 |

**23분이 지나도 아무것도 안 바뀐다.** `FAILED` 로 가지도, 알림함에 줄이 생기지도,
로그에 `발송시도` 가 한 줄 남지도 않는다.

## 5. 밀려서 유실에 이르는가 — 2026-08-30

`scripts/06_backlog_setup.sql` · `07_backlog_count.sql`

4번은 **이미 만료된 뒤**를 봤다. 여기서는 **밀려서 만료에 이르는 과정**을 재현한다.

### 왜 500건으로는 안 되나

조회에 `LIMIT` 가 없어서 한 번에 다 집어간다. 500건이 199초 걸려도 그 실행 안에서
전부 나간다. **유실은 "집히기 전에 방치된 것" 에만 생긴다.**

그래서 두 덩이로 나눴다.

```
홀딩   2,500건을 지금 시각으로     스케줄러를 오래 붙잡는다
유입     200건을 1~20분 뒤로 10건씩  붙잡힌 동안 도착해 방치된다
```

발송은 진짜 FCM 으로 했다. **기기의 앱 알림만 꺼두면** 왕복은 그대로고 화면만
조용하다. `users_settings` 를 끄면 조회에서 걸러져 발송 자체가 안 되므로 그쪽이
아니다.

### 실행 기록

```
14:31:00   조회 count=2500   →  770.7초(12.8분) 처리
14:44:00   조회 count=100    oldest=14:34
14:45 ~ 14:51   count=10 씩
```

### 결과

| 구분 | 전체 | 발송됨 | 대기중 |
|---|---|---|---|
| 홀딩 | 2,500 | 2,500 | 0 |
| 유입 | 200 | 170 | **30** |

유입을 분별로 보면 경계가 정확히 갈린다.

| 몇 분 뒤 | 울릴 시각 | 결과 |
|---|---|---|
| 01분 | 14:31:59 | 대기중 |
| 02분 | 14:32:59 | 대기중 |
| 03분 | 14:33:59 | 대기중 |
| **04분** | **14:34:59** | **발송됨** |
| 05 ~ 20분 | ~ 14:50:59 | 발송됨 |

`14:44` 틱의 `oldest` 가 `14:34` 다. **`14:33:59` 는 그보다 앞이라 창 밖, `14:34:59`
는 안쪽이다.** 30건이 갈린 자리가 여기다.

산수와도 맞는다.

```
12.8분 밀림 − 10분 창 = 2.8분치가 창 밖
2.8분 × 분당 10건 = 28건  ≈  30건
```

### 유실된 30건에 아무 기록이 없다

```
status              PENDING
attempt_count       0
last_error_code     NULL
알림함 줄            없음
```

**시도조차 안 했다.** 4번에서 본 것과 같은데, 이번에는 **실제로 밀려서** 그렇게 됐다.

### 처리율이 지난번보다 빨랐다

```
이번    2,500건 / 770.7초  =  3.24 건/초  =  분당 195건    1건 중앙값 284 ms
지난번  100 ~ 500건        =  2.5 ~ 2.9   =  분당 150~175   1건 중앙값 330 ms
```

**건수를 다섯 배로 늘렸는데 오히려 빨랐다.** 그러면 1번의 "500건만 어긋난다" 도
배치 크기 탓이 아니라 **FCM 왕복 시간이 날마다 다른 것**으로 읽힌다.

한계는 **분당 150 ~ 195건**으로 넓혀 잡는 게 맞다.

### 곁가지 — 한 건의 예외가 실행 전체를 끝낸다

세팅을 두 번 돌린 탓에 이런 예외가 났다.

```
14:30:59  ObjectOptimisticLockingFailureException:
          Row was updated or deleted by another transaction [UserNotification#3103]
```

첫 실행이 처리 중일 때 두 번째 실행의 정리 구문이 그 행을 지웠다. **그 실행은
거기서 끝났다.** 173건만 나가고 나머지는 그대로 남았다.

`checkAndSendAlerts` 의 루프에 `try/catch` 가 없다. **한 건이 터지면 그 실행의
나머지가 통째로 버려진다.** 상태 기반이라 다음 틱에 회수되지만, 밀린 상황에서는
그만큼 더 밀린다.

> `06_latency.py` 의 `[1] 14:30:00` 항목은 이 죽은 실행이다. 실험은 `[2]` 다.

## 6. 타임아웃 계산

관측이 아니라 **설정값으로 계산한 것**이다.

```java
// FcmConfig
.setConnectTimeout(3_000)
.setReadTimeout(5_000)
```

```
한 건 평균 = (1 − 타임아웃 비율) × 0.4초  +  타임아웃 비율 × 5초
10분 ÷ 한 건 평균 = 10분 안에 비울 수 있는 양
```

| 타임아웃 비율 | 한 건 평균 | 10분 안에 비울 양 |
|---|---|---|
| 0 % | 0.40 초 | 1,500건 |
| 1 % | 0.45 초 | 1,340건 |
| 5 % | 0.63 초 | 950건 |
| 10 % | 0.86 초 | 700건 |
| 50 % | 2.70 초 | 220건 |
| 100 % | 5.00 초 | 120건 |

`0.4초` 는 네 라운드 중 **가장 느렸던 500건**(RPS 2.51)에서 역산했다. 빠른 쪽
(0.345초)으로 계산하면 `1,740 → 740` 이 되는데, **어느 쪽을 써도 절반 이하**라
불리한 값을 썼다.

실패 한 건의 실제 소요는 재보지 못했다. 만들 수 있는 실패(가짜 토큰)는 FCM 이 형식만
보고 거절하는 **빠른 실패**라 재고 싶은 것과 다르고, 느린 실패(APNs 경유)는 Firebase
설정을 일부러 깨야 나온다.

## 7. 동시성 N 을 올려가며 — 2026-09-03

`scripts/after-scheduler-speed/` · 1,000건을 심고 N 만 바꿔 같은 순서로 돌린다.

### 왜 세 사람에게 나눠 보내나

FCM 은 **한 기기에 분당 240건**까지만 받는다. 한 사람에게 몰면 N=2 부터 우리 코드가
아니라 FCM 의 스로틀링을 재게 된다.

```
users_id  32    IOS 18.6
users_id  33    IOS 26.6.1
users_id 265    ANDROID 16
```

세 대면 분당 720건까지 안전하다. **N=8 위쪽은 기기당 400건이 되어 이 방법으로
못 잰다.**

### N = 1 — 기준선

```
설정        alarm.send.concurrency=1
심은 양     1,000건  (333 · 334 · 333 으로 나눔)
구간        16:32:00 ~ 16:36:46
```

| | 값 |
|---|---|
| 처리 시간 | 286.5 초 |
| 분당 | **209건** |
| 1건 중앙값 | 316 ms |
| 1건 p95 | 383 ms (96 ~ 1,325 ms) |
| FCM 구간 중앙값 | 305 ms |
| 실효 동시성 | 1.1 |
| 발송됨 / 대기중 / 포기 | 1,000 / 0 / 0 |

실효 동시성은 `분당 ÷ 60 × 1건 시간` 으로 되짚은 값이다. 스레드 개수와 맞으므로
**측정이 어긋나지 않았다.** N 을 올렸을 때 이 값이 안 따라 오르면 그때가 병목이다.

세 기기 모두 전량 발송됐다. 한쪽만 실패가 몰리지 않았으니 240건 제한에 안 걸렸다.

| 사용자 | 전체 | 발송됨 | 대기중 | 포기 |
|---|---|---|---|---|
| 32 | 333 | 333 | 0 | 0 |
| 33 | 334 | 334 | 0 | 0 |
| 265 | 333 | 333 | 0 | 0 |

### 자원 — 전부 바닥이다

그래프 : `images/N1/` (16:29 ~ 16:43)

| 패널 | 파일 | 값 |
|---|---|---|
| 커넥션 풀 | `connection-pool.png` | 상한 10 · 대기 **0** · 평균 사용 **0.154** |
| 커넥션 획득 | `connection-use.png` | 최고 22 ms · 타임아웃 **0** |
| CPU | `cpu.png` | 평소 1.2 % → 최고 **12.8 %** |
| 사용자 API p95 | `userp95.png` | 18 ~ 25 ms |

**풀 10 개 중 평균 0.154 개를 쥐었다.** 대기는 0 이다. 이게 기준선이고, N 을 올려
이 값들이 어떻게 움직이는지가 상한을 정한다.

CPU 12.8 % 는 2 vCPU 기준이다. 8월 29일 500건 라운드의 10.4 % 와 비슷하다.
**건수를 두 배로 늘려도 봉우리 높이는 그대로고 폭만 늘어난다** — 1번·2번에서 본
것과 같다.

> **`hikaricp_connections_active` 는 쓰지 않았다**
> 그 지표는 스크랩 순간을 찍는 게이지다. 한 건 316 ms 중 DB 를 쥐는 시간이
> 50 ms 남짓이라 평균 점유가 0.15 개인데, **게이지는 0 아니면 1 로만 찍힌다.**
> 실제로 N=1·2·4 세 라운드 모두 0 으로 나와서 아무것도 못 읽었다.
>
> 대신 커넥션을 쥔 **시간의 합**을 쓴다. 단위가 `초/초` 라 그대로 평균 동시 사용
> 개수가 되고, 스크랩이 언제 떨어지든 놓치지 않는다.
>
> ```promql
> rate(hikaricp_connections_usage_seconds_sum{application="toit-test"}[1m])
> ```

> **사용자 API p95 는 이 라운드에서 근거가 못 된다**
> 16:33 · 16:34 두 점 말고는 아예 값이 없다. 그 시간에 API 호출이 없었다는 뜻이다.
> **"스케줄러가 사용자를 안 방해했다" 를 이 그래프로 주장할 수 없다.** 방해할
> 트래픽 자체가 없었다.

## 8. 만료가 기록에 남는가 — 2026-09-07

4번과 **같은 스크립트**(`scripts/01_expired_setup.sql`)를 `markExpired` 를 넣은 뒤에
다시 돌렸다. 입력이 같고 결과만 달라지므로 개선 전후 비교가 된다.

```
세팅        200건을 11분 전 시각으로,  status = PENDING
```

### 로그

```
15:31:00.166  WARN  [ALARM] 만료 count=200 oldest=2026-09-07T15:21
15:31:00.269  INFO  [ALARM] 조회 now=15:31 oldest=15:21 count=0
15:32:00.082  INFO  [ALARM] 조회 now=15:32 oldest=15:22 count=0
```

- **한 바퀴 만에 200건이 다 잡혔다.** 4번에서는 23분을 기다려도 아무것도 안 바뀌었다.
- `조회 count=0` — 만료된 것은 발송 대상에서 빠진다. 두 쿼리가 겹치지 않는다.
- **15:32 에는 `만료` 줄이 아예 없다.** 조건이 `status = PENDING` 이라 다시 안 걸린다.

### 상태

| | 4번 (개선 전) | 8번 (개선 후) |
|---|---|---|
| 전체 | 200 | 200 |
| 대기중 (`PENDING`) | **200** | 0 |
| 만료됨 (`EXPIRED`) | — | **200** |
| 발송됨 (`SENT`) | 0 | 0 |
| 시도한 적 있음 | 0 | **0** |

**`시도한 적 있음` 이 0 인 것이 중요하다.** FCM 을 한 번도 안 타고 상태만 바꿨다는
뜻이다. 만료 표시가 발송 경로에 부담을 주지 않는다.

### 걸린 시간

```
15:31:00.0xx  스케줄러 깨어남
15:31:00.166  만료 200건 표시 완료
```

벌크 UPDATE 한 문장이라 **200건에 0.2초가 안 걸린다.** 건수가 늘어도 FCM 을 안 타므로
발송과 달리 선형으로 늘지 않는다.

### 얻은 것

`slo.md` 에서 *"유실은 어디에도 없다"* 고 적어둔 칸이 채워진다.

| | 로그 | 지표 |
|---|---|---|
| 지연 | 있다 | 없다 |
| 유실 | **있다** (`[ALARM] 만료 count=`) | 없다 |

지표(`alarm_expired_total`)는 아직 없다. 로그로는 세지만 그라파나에 안 뜬다.

| 200 | 341 ms | 2.9 | 2.8 |
| 300 | 330 ms | 3.0 | 2.9 |
| 500 | 295 ms | **3.4** | **2.5** |

한 건 자체는 오히려 빨랐는데(295 ms) 전체는 느렸다. 건 사이의 틈도 아니었다(11~13 ms).
남는 설명은 **꼬리**다. `p95` 가 300건 400 ms 에 견줘 500건은 869 ms 로 두 배다.
중앙값은 꼬리를 못 본다.

원인은 더 갈라보지 않았다. FCM 이 외부라 3분 넘게 도는 동안 응답이 출렁일 여지가
있고, 이 글의 결론(하나씩 보내서 느리다)은 앞의 세 라운드로 충분하다.

### 조회에 상한이 없다

```java
List<SchedulesAlarm> alarms = schedulesAlarmRepository.findTargetAlarms(now, oldest);
```

`LIMIT` 도 `Pageable` 도 없다. 밀린 것을 전부 한 번에 메모리로 올린다. 500건까지는
재봤지만 **1,500건을 한 번에 들 수 있는지는 안 재봤다.** 힙은 이번 측정에서 보지
않았다.
