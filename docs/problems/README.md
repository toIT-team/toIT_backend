# 개선 대상 문제 목록

다룰 문제를 **동시성과 정합성** 한 축으로 모으고, 포트폴리오 값 기준으로 우선순위를 매겨 정리한다.

## 왜 이 축인가

기존에 해결한 문제(이미지 업로드, CDN 조회, 검색 최적화, Rate Limiter)는 모두
**"느리다 → 측정으로 병목 특정 → 인프라 기능 적용"** 유형이었다.

측정 방법론은 일관됐지만 소재가 매번 달라(S3 → CloudFront → PostgreSQL → NGINX)
"무엇을 하는 사람인지"가 드러나지 않았고, CS 지식으로 파고들 입구도 검색(인덱스) 하나뿐이었다.

동시성을 축으로 잡으면 흩어져 있던 경험이 하나로 이어진다.

| 시점 | 경험 | 레벨 |
|---|---|---|
| 2023~2024 | Ecole 42 — mutex, semaphore, 식사하는 철학자(교착상태) | C / OS |
| 2025 | 블루넥스 인턴 — 10만 건 발송의 중복 수신, 유실 | 실무 / 대량 처리 |
| **2026** | **toIT — 경쟁 조건, 원자성, 외부 의존 격리** | **애플리케이션 / DB** |

동시성은 좁은 주제가 아니라 **DB·OS·네트워크로 모두 이어지는 허브**다.

- **DB** — 트랜잭션 ACID → 격리수준 → 이상현상 → MVCC → 락 → 데드락 → 낙관/비관락
- **OS** — 스레드, 컨텍스트 스위칭 → 뮤텍스·세마포어 → 데드락 4조건 → 원자적 연산, CAS
- **네트워크·분산** — 멱등성 → at-least-once / exactly-once → 분산 락 → 재시도와 타임아웃

## 문제 우선순위

**할 일 순서가 아니라 "포트폴리오에 넣었을 때 값" 순서다.**
판단 기준은 넷 — 겹치지 않는가 / 측정 가능한가 / 진짜 문제인가 / 축에 맞는가.

### 1. 스토리지 한도 경쟁 조건 — 완료

→ [storage-limit/](storage-limit/)

| | |
|---|---|
| **강점** | 재현 곡선(동시 2→15MB, 10→135MB), 반증(`@Transactional`·REPEATABLE READ 로도 안 막힘), 검증(락 대기 = N−1), 비용(p95 228→209ms) |
| **약점** | 대안 6종 중 5종을 논증으로 기각. **실측이 하나뿐** |
| **보완** | `@Transactional(isolation = SERIALIZABLE)` 한 줄 바꿔 `run_curve.sh` 재실행. 반나절 |

**아직 드러내지 않은 무기** — `FOR UPDATE` 를 걸어도 **트랜잭션의 첫 DB 접근이 아니면 무력해진다**는 발견.
REPEATABLE READ 에서 스냅샷이 첫 일반 조회 시점에 확정되기 때문이다.
지금은 3절 안쪽 한 문단에 묻혀 있다. **별도 글로 뽑을 것.**

### 2. 링크 프리뷰 — 스레드 점유와 SSRF — 미착수

→ [link-preview/](link-preview/)

**두 겹이라 강하다.**

```
성능   timeout 4초 × UA 2회 = 최악 8초 톰캣 스레드 점유 (max-threads 기본 200)
       남의 서버 사정이 우리 처리량을 정한다
보안   URL 검증 코드 0줄 + followRedirects(true)
       → http://169.254.169.254/latest/meta-data/ 로 IAM 자격증명 노출 가능
```

- 스레드 점유는 흔한 소재지만 **SSRF 를 함께 다룬 사례는 비교군에 없다**
- 지금 동작 중인 기능이고 검증 코드가 실제로 없다 — 만들어낸 문제가 아니다
- `refactor(link-preview)` PR 의 `남은 과제` 에 본인이 적어둔 것을 지키는 서사

**측정** — 느린 사이트를 섞어 동시 요청 → 스레드 점유율, 같은 시각 다른 API 의 p95 변화

### 3. 폴더 삭제 — 트랜잭션 경계 부재 — 미착수

`@Transactional` 이 하나도 없는 서비스가 5개다.
`LinksService` · `TextsService` · `FoldersService` · `SchedulesService` · `UserNotificationService`

Spring Data JPA 의 `save()` 에는 `@Transactional` 이 붙어 있어 **호출마다 개별 커밋**된다.

```java
// FoldersService.deleteFolders — 여섯 덩어리가 전부 별개 트랜잭션
schedulesRepository.saveAll(schedules);   // ①
textsRepository.saveAll(texts);           // ②
linksRepository.saveAll(links);           // ③
    ...
    if (activeCount == 0) s3Storage.delete(objectKey);   // ④ 롤백 불가
attachMentsRepository.saveAll(attachMents);              // ⑤
foldersRepository.save(folder);                          // ⑥
```

④ 이후 실패하면 **S3 파일은 영구 소실되고 DB 행은 ACTIVE 로 남는다.**
사용자 화면에는 보이는데 열면 깨지는 상태이며 복구할 수 없다.

- **비교군에 트랜잭션 경계를 다룬 사례가 없다**
- 스토리지는 격리(Isolation), 이건 원자성(Atomicity) — **ACID 두 글자**
- 회원 탈퇴(`UsersWithdrawService`)에서는 `afterCommit` 으로 **이미 같은 원칙을 적용했다.**
  한쪽은 알고 한쪽은 놓친 상태 → *"한 곳에서 세운 원칙을 전수 점검으로 확대"* 라는 서술이 가능
- 판단거리 — S3 삭제를 트랜잭션 안에 두면 롤백해도 파일이 안 돌아오고,
  밖에 두면 커밋 후 실패 시 고아 객체가 남는다. **어느 오류가 덜 나쁜지 고르는 문제**

**약점** — 부하 곡선이 아니라 실패 주입이라 숫자 임팩트가 작다.

### 4. 초과 트래픽 차단 — 완료

**의외로 차별점이다.** 비교군은 전부 "빠르게 만드는" 쪽이고
**넘치는 트래픽을 앞단에서 버린다**는 발상을 다룬 사례가 없다.

`요청은 뒤로 갈수록 비싸므로 NGINX 에서 차단` 이라는 판단 근거도 명확하다.

### 5. 통합검색 병목 3개 — 완료

`async-profiler 를 inclusive 로 바꿔 숨은 S3 서명 생성(CPU 42.6%) 발견` 이 가장 좋은 대목이다.
**도구 설정을 바꿔서 안 보이던 것을 찾아낸 기록.**

**약점** — 쿼리 최적화는 비교군에 더 깊은 사례가 있다(실행계획 3단계 분석 + 실제 SQL, 700배).
정면으로 붙으면 불리하므로 **이력서에만 두는 것도 방법.**

### 6. 알림 스케줄러 — 유실과 중복 — 조건부

→ [notification-scheduler/](notification-scheduler/)

```java
if (isSent) { userNotificationService.markAsSent(notification); }
alarm.markAsSent();     // ← 조건 밖. 발송 실패해도 완료 처리 = 영구 유실
```
```sql
WHERE alarmDateTime >= :now AND alarmDateTime < :nextMinute   -- 그 1분만. 재시작하면 소실
```

`@Scheduled` 에 인스턴스 락이 없어 서버를 늘리면 전량 중복 발송된다.
(같은 뿌리로 `AttachmentReservationCleaner` 도 해당)

**블루넥스 인턴 항목과 정면으로 대비된다.** 같은 중복·유실 문제를
10만 건 / 인프라 자유에서는 RabbitMQ 로, 분당 수 건 / 2GB 단일에서는 다르게 답하는 구도.
**Kafka·RabbitMQ 를 실측 후 기각하는 자리가 여기다.**

**전제** — 기능이 통째로 비활성화되어 있다(`0b52b59`).
다시 켜는 것은 서비스 판단이며, 포트폴리오 때문에 켠다면 순서가 거꾸로다.

### 7. CloudFront 서명 범위 — 미착수

```java
// CloudFrontSigner.java:45
String resourceUrl = domain + "/*";     // 한 사용자 쿠키로 도메인 전체 파일 접근 가능
```

인가(Authorization) 취약점이고 비교군에 사례가 없다.
다만 고치는 것이 한 줄이라 **단독 항목으로는 짧다.** CDN 서빙 복구 작업과 묶을 것.

### 8. 이력서 전용

| | |
|---|---|
| **PostgreSQL → MySQL 전환** | 인덱스 5개 유실 발견, 미사용 컬럼 6개, **한글 이중 인코딩을 `HEX()` 로 검출**. 검증할 줄 안다는 신호 |
| **모니터링 체계** | Prometheus·Micrometer·Grafana. 측정할 지표를 먼저 정하고 붙였다는 서술 |

### 다루지 않을 것

| | 이유 |
|---|---|
| Kafka · MSA 별도 프로젝트 | 2 vCPU / 2GB 에 브로커가 들어가지 않고, 해결할 문제도 없다. **알림 항목의 대안으로만 실측 후 기각** |
| 멀티 모듈 | 개발자 1명, 배포 단위 하나. 정당화 불가 |
| 구버전 업로드 경로 | 앱이 presign 경로만 쓴다면 **엔드포인트를 지우는 것이 답** |
| 크기 신뢰(`HeadObject`) | 단독 항목 아님. 스토리지의 `한계` 를 지우는 마무리 |
| 폴더 존재 확인 check-then-act | 곁가지. 결과가 한도 초과가 아니라 고아 행 |

## 비교 분석 — 어디가 겹치고 어디가 비는가

비슷한 경력의 백엔드 지원자 3인의 이력서·포트폴리오를 읽고 정리했다.

| 주제 | A | B | C | 우리 |
|---|---|---|---|---|
| 락 · 동시성 | ✅ | ✅ | — | ✅ **측정 우위** |
| 스레드 풀 점유 | ✅ | — | ✅ | ⬜ 예정 |
| 캐시 전략 | ✅ | ✅ | ✅ | — |
| 쿼리 최적화 | ✅ **강함** | ✅ | — | ✅ 밀림 |
| GC · 자원 효율 | — | ✅ | — | — |
| 오픈소스 기여 | — | — | ✅ **압도** | — |
| 장애 격리 · 폴백 | ✅ | — | ✅ | — |
| **트래픽 셰딩** | — | — | — | ✅ **유일** |
| **SSRF · 보안** | — | — | △ | ⬜ **유일** |
| **트랜잭션 원자성** | — | — | — | ⬜ **유일** |
| **인가 범위** | — | — | — | ⬜ **유일** |

**아래 네 줄이 우리만 가진 자리다.** 위쪽 겹치는 주제로는 이기기 어렵다.

### 배울 점

**1. 중간 단계를 남긴다.**
`7,836 → 148 → 35ms`, `1,400 → 300 → 100 → 2ms` 처럼 **여러 번 시도한 기록**을 보여준다.
스토리지 항목도 예약 구조 → 비관적 락 두 단계를 밟았는데 `135MB → 0` 한 줄로만 적혀 있다.

**2. 응답시간 말고 다른 지표도 쓴다.**
비용($), 연산 수, Redis 명령 수, STW, 스레드 풀 포화 비율.
우리는 `락 대기 횟수` 라는 좋은 지표를 이미 쓰고 있으니 **비용이나 자원 사용량**을 하나 더한다.

**3. 대안은 구현해서 기각한다.**
가장 강한 사례는 Virtual Thread · PER · Soft TTL 을 **전부 구현해 측정하고 표로 비교**했다.
우리는 대안 6종 중 5종을 논증으로 떨어뜨렸다. **최소한 SERIALIZABLE 하나는 실측할 것.**

**4. 스스로 규모를 깎지 않는다.**
비교군 중 둘도 실사용 트래픽이 아니라 **부하를 만들어(100만 건, 1,000VU) 측정**했다.
우리와 같은 방식이다. 그런데 우리 문서에는 `실제 위험도` 절이 따로 있어
`사용자 28명`, `실제 피해는 작다` 를 먼저 말하고 있다.
**정직은 `한계` 절 한 줄로 충분하다.**

**5. 문제 코드를 3줄만 보여준다.**
가장 좋은 사례는 문제가 된 메서드를 3줄 그대로 붙여 놓았다. 다이어그램보다 빠르다.
문서 1절은 일반 독자용이라 코드가 없는 게 맞지만, **포트폴리오는 개발자가 읽는다.**

## 추천 구성

```
1. 동시성과 정합성
   1.1 블루넥스 인턴 — 10만 건 발송의 중복·유실        있음
   1.2 스토리지 한도 — 격리(Isolation)                완료 · SERIALIZABLE 실측 추가
   1.3 폴더 삭제 — 원자성(Atomicity)과 롤백 불가 작업   신규 · 3~5일

2. 성능과 용량
   2.1 초과 트래픽 차단                               있음
   2.2 링크 프리뷰 — 스레드 점유와 SSRF                신규 · 1~2주

3. 명세를 읽고 구현하기
   3.1 RFC 6749 OAuth 2.0                            있음
```

축이 **격리 → 원자성 → 자원 보호 → 외부 의존 격리 + 보안** 으로 이어져
한 사람의 관심사가 선명하게 읽힌다.

**통합검색은 이력서에만.** 비교군에 더 깊은 쿼리 최적화 사례가 있어 포트폴리오에서 붙으면 불리하다.

## 작업할 때 지킬 것

### 1. 재현 테스트를 먼저 만든다

동시성은 **"말로만 아는 상태"** 가 되기 가장 쉬운 주제다. 격리수준 4개는 누구나 외운다.
차별화는 **실제로 깨뜨려보고 숫자로 남긴 것**에서 나온다.

- ❌ "동시 요청 시 용량 제한이 초과될 수 있습니다"
- ✅ "동시 2 요청에서 15MB, 동시 10 요청에서 135MB 초과했고 그 이상은 커넥션 풀이 상한이었습니다"

부하는 **NGINX Rate Limiter 를 우회해 앱 포트로 직접** 보낸다.
`limit_req` 가 요청을 잘라내면 애플리케이션 레벨 측정이 안 된다.

JIT 워밍업 전에는 값이 2~3배로 나온다. **측정 전 200요청을 흘려보낸다.**

### 2. 대안은 논증이 아니라 실측으로 고른다

**채택하지 않을 것도 최소 하나는 구현해서 잰다.**
"과해 보여서 안 썼다"와 "띄워보니 브로커만 ○○MB 였고 우리 발송량엔 ○○로 충분했다"는 다르다.

락 계열은 커넥션 점유가 핵심 비용이므로
`hikaricp_connections_active` / `pending`, `Innodb_row_lock_waits` / `_time` 을 함께 본다.

### 3. 실패한 시도와 한계를 기록한다

"이 방법을 써봤는데 기대만큼 개선되지 않았다", "여기까지는 되고 여기부터는 안 된다"는
서술이 신뢰를 만든다. 채택한 것만 적으면 처음부터 정답을 알았던 것처럼 보여 오히려 얕게 읽힌다.

스토리지 항목의 `총 대기 ÷ (1+2+…+N-1)` 역산 실패가 좋은 예다.

### 4. 규모는 밝히되 앞세우지 않는다

정직하게 적되 **`한계` 절 한 줄**로 충분하다. 절을 따로 두어 먼저 말하면
스스로 항목의 값을 깎는다.

### 5. 문서 형식

```
문제 상황 → 고려한 대안과 탈락 이유 → 해결 과정 → 결과 → 한계
```

- 이력서는 `[문제 상황] / [해결 과정] / [결과]` 3줄 고정 + 상세 링크
- 포트폴리오는 대안 비교표와 판단 근거까지
- `docs/problems/` 는 측정 원본
- 해결 후 각 폴더의 `blog/` 에 쓴 글이 이력서의 링크 대상이 된다
