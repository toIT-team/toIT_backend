# SLO · SLI

# 1. 알림

## 약속

```
사용자가 설정한 시각으로부터 10분 안에 나간다
그중 대부분은 1분 안에             (p95) = 알림 100개 중 95개는 1분안에 나간다.
10분을 넘겨 버려지는 것은 없다      (유실률 0 %)
```

## 왜 10분인가

```
그쯤까지는 "좀 늦었네" 지만 그 뒤로는 "고장났네" 로 읽힌다
재시도 3회가 1 + 2 + 4 로 7분을 쓰므로 그 안에 들어가야 한다
```

공식 기준은 없다. FCM 문서가 짧은 TTL 이 필요한 예로 캘린더 알림을 들지만 몇 분으로
하라는 말은 없다. **우리가 정한 값이고**, 코드에서는 `NotificationScheduler.VALID_MINUTES`
가 이 값이다.

## 지연과 유실은 같은 사건이다

10분을 넘긴 것은 **보내지 않고 버린다.** 그래서 선을 넘는 순간 지연이 곧 유실이 된다.
지표를 둘로 나눠 놓았지만 경계는 하나다.

FCM 이 거부한 것(`FAILED`)은 유실로 세지 않는다. 기록이 남고 사용자에게 설명할 수 있다.

## 무엇으로 재나

```
alarm_delay_seconds     실제 발송 시각 − 울릴 시각    버킷 1분 · 5분 · 10분
alarm_expired_total     10분을 넘겨 버려진 건수
alarm_sent_total        발송된 건수

유실률 = expired / (sent + expired)
```

## 아직 못 잰다

| | 로그 | 지표 |
|---|---|---|
| 지연 | 있다 | 없다 |
| 유실 | **없다** | 없다 |

- **지연** 은 로그로 계산된다. `발송시도` 줄의 `예정=` 이 울릴 시각이고 `발송성공` 줄에
  실제 시각이 찍힌다. 다만 사람이 로그를 받아 스크립트를 돌려야 하고 그라파나에 안 뜬다.
- **유실** 은 어디에도 없다. 만료된 알림은 조회에서 빠질 뿐 `FAILED` 로 바뀌지도, 로그가
  남지도 않는다. 세려면 그것을 집어서 표시하는 주체가 있어야 하는데, 조회에서 빠진
  뒤로는 아무도 집으러 오지 않는다.

그래서 `99.9%` 같은 오차 예산은 안 정했다. **셀 수 있게 된 뒤에 정한다.**

지금 이 값들은 **설계 기준**이다. *"이 조건을 만족하도록 만든다"* 이지 *"한 달에 몇 번까지
어겨도 된다"* 가 아니다.
